## Measurement Report: `response_format` 対応の実測（REQ-F-016 / Phase 0）

本レポートは REQ-F-016 / AC-016 の実測ゲートの記録です。`specifications-structured-output.md`
§4.1.1 および §4.2 が本レポートを唯一の実測記録として参照します。

**結論**: 対象サーバは `response_format`（`json_schema` / `strict: true`）を **準拠（honoured）**
として扱います。実測した 9 組すべてで 10/10 の準拠率であり、DR-25 の合格線（測定した組すべてで
10/10）を満たします。モデル差の 3 組は測定していません（DR-31）。

## 2. 測定内容

`specifications-structured-output.md` §4.2 が定める 3 種のスキーマと、モデル差を除く 3 条件を
組み合わせた 9 組について、各 10 回試行しました（計 90 リクエスト）。

| スキーマ | §4.2 の種別                | 契約定義（§4.3.1）の写し                                                    |
| -------- | -------------------------- | --------------------------------------------------------------------------- |
| envelope | 配列を包む object envelope | #1 相当。`items` に `file` / `project` / `confidence` / `reason` を持つ要素 |
| enum     | enum を含む object         | #6 相当。`type` / `category` を辞書由来の enum で拘束                       |
| yaml     | YAML 契約に対応する object | #4 相当。`title` / `topics` / `tags`。配列要素を辞書由来の enum で拘束      |

enum の値域は `.config/chatlog-exporter/dics/` の実辞書から実行時に読み込みました
（`projects.dic` 全キー + `misc`、`types.dic` 全キー、`category.dic` 全キー、`topics.dic` 22 件、
`tags.dic` 73 件）。スキーマは §4.3 の形を守り、root を object、`additionalProperties: false`、
全プロパティ required、数量制約なしとしています。

| 条件          | 入力                                                                 |
| ------------- | -------------------------------------------------------------------- |
| 長文入力      | 実運用のチャンク上限（`maxContentLength` 4000 文字）に近い日本語ログ |
| enum 境界     | 開発と無関係な日本語ログ。正解がフォールバック値のみになる入力       |
| 非 ASCII 往復 | 絵文字・全角記号・丸囲み数字・旧字体・濁点を含む日本語ログ           |

準拠の判定は「HTTP 2xx」「本文が JSON」「`choices[0].message.content` が文字列」
「その文字列が JSON として parse できる」「§4.3.1 の required keys と値の型に一致」
「余剰キーがない」「enum フィールドが値域内」「`finish_reason` が `stop`」の全充足としました。

### 3.1 `finish_reason` の実値分布（DR-25 決定 3）

90 回すべて `stop` でした。`length`・`eos`・`end_turn` などの実装固有値、および欠落・`null` は
一度も観測されていません。

| `finish_reason` | 回数 |
| --------------- | ---- |
| `stop`          | 90   |

### 3.2 HTTP ステータスと Content-Type

90 回すべて `200` / `application/json; charset=utf-8` でした。**HTTP 400 は 1 件も発生していません。**
したがって `response_format` の拒否とコンテキスト長超過を読み分ける条件は、本実測から決められません
（§5 の未決を参照）。

### 3.3 非 ASCII 往復（AC-021 の受信側）

90 件の応答本文に U+FFFD（置換文字）の混入は 0 件でした。絵文字・全角記号・丸囲み数字・旧字体を
含む入力に対し、生成された日本語の `title` が無損失で往復しています。

### 3.4 enum 境界（R-003 の目的）

| スキーマ | 結果                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| envelope | 10/10 で `project` にフォールバック値 `misc`（`FALLBACK_PROJECT`）を選択       |
| enum     | 10/10 で `type` が `research`、`category` が `development`（それぞれの既定値） |
| yaml     | 10 回中 4 回が `topics` / `tags` を空配列、残り 6 回は値域内の値を選択         |

単一値の enum は、フォールバック値が値域に含まれていれば確実に選択されます。配列要素の enum は
「該当なし」を空配列で表す規定であり、空配列を強制しません。したがって値域内の値が選ばれた 6 回も
契約適合です（§4.3.1「配列値の enum」）。

### 3.5 スループット（参考値）

実プロンプト（`meta.yaml` + `topics.dic` 整形 + `tags.dic` キー + 4000 文字本文）での内訳を
別途測りました。

| 項目                                   | 値                                               |
| -------------------------------------- | ------------------------------------------------ |
| プロンプト処理                         | 6,149 トークン / 97 tok/s（約 63 秒）            |
| 生成                                   | 96 トークン / 15 tok/s                           |
| 合計（プロンプトキャッシュ未ヒット）   | 70.1 秒                                          |
| 同一プロンプト再送（キャッシュヒット） | 5.3 秒                                           |
| 5 ファイル一括（filter 相当）          | 10,491 トークン / 87 tok/s + 生成 2,211 トークン |

律速はプロンプト処理です。プロンプトテンプレートは可変値（`log_type` / `log_category`）を
辞書一覧より前に置いているため、ファイル間でプロンプトキャッシュが効きません。辞書を前に置けば
6,000 トークン分の前処理を再利用でき、実測では 70.1 秒が 5.3 秒になりました。本スコープ外の
改善であり、別途起票します。

## 4. thinking の無効化が必須である理由

対象モデルは thinking モデルです。既定の起動状態ではモデルが推論ブロックを生成し、その長さに
上限がありません。生成速度が約 15 tok/s であるため、これが `timeoutMs`（300 秒）を超えます。

| 起動状態                                             | 実運用相当の呼び出し                              |
| ---------------------------------------------------- | ------------------------------------------------- |
| 既定（`<think>` 前置あり）                           | 推論 5,000〜7,000 トークン超。150 秒で打ち切り    |
| `<think>` 前置のみ除去                               | 推論 7,320 文字。5 呼び出し中 3 件が 300 秒に到達 |
| `--chat-template-kwargs '{"enable_thinking":false}'` | 推論 0 文字。本レポート §3 の値                   |

リクエスト単位の `reasoning_budget: 0` は無視されました。DR-15 がボディを 4 フィールドに
限定しているため、アプリ側から thinking を切る手段はありません。**このフラグは対象サーバの
前提条件であり、欠けた構成は対応対象外とします。**

## 6. 再現手順

1. `--chat-template-kwargs '{"enable_thinking":false}'` 付きで llama.cpp server を起動します。
2. `GET /props` で `generation_prompt` が空文字列であることを確認します。
3. 3 種のスキーマ × 3 条件 × 10 試行を同時実行数 4 で送ります。ボディは 4 フィールドのみとします。
4. §2 の判定条件で準拠を数え、`finish_reason` の実値分布を併せて記録します。

生データ（90 件の試行ログと集計）は測定時の作業ディレクトリに置いた一時ファイルであり、
リポジトリには含めません。本レポートの §3 が記録として正です。

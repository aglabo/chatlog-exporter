## Measurement Report: 生成長のばらつきと生成パラメータ（temperature / max_tokens）の実測

本レポートは beads `cle-kju.3.3.6` / GitHub [#478](https://github.com/aglabo/chatlog-exporter/issues/478) の実測記録です。
`measurements-context-limits-2026-09-29.md` §3.4 / §5.2 が「`temperature` 1.0 かつ `max_tokens` 非送信（DR-15）
のため生成長が 249〜749 tok と振れる」として残した課題を測りました。

**結論**:

- **`temperature` を下げても生成長の幅は縮みません。** filter × 8000 の幅は 1.0 で 228〜302 tok、0.3 で 247〜321 tok と
  ほぼ同じです。むしろ 0.0 と 0.3 では filter × 12000 で **暴走**（`max_tokens` 到達まで生成し続ける）が出ました。
  `temperature` は送らずサーバ既定に委ねたままとします
- **12000 で生成長が伸びて振れる原因は温度ではなく、応答要素の過多です。** 判定対象外のファイルを `items` に足し続けます
  （`measurements-context-limits-2026-09-29.md` §5.3 の取り違えと同じ現象）
- **サーバは `n_predict: -1`（無制限）です。** クライアントが `timeoutMs` で打ち切ってもサーバ側の生成は止まらず、
  `--parallel 1` の唯一のスロットを占有し続け、後続のリクエストを待たせます。暴走の上限を決めるのは `max_tokens` しかありません。
  出力契約ごとの `max_tokens` を安全弁として送ると決めました（DR-37）

## 2. 測定内容

ハーネスは `temp/cle-kju336/run.ts` の使い捨てです（未コミット）。production の
`processChunk`（filter）・`judgeTypeAndCategory`（type-category）・`generateFrontmatter`（meta）を
そのまま呼び、`runAI` の `fetchProvider` でリクエストボディに `temperature` と `max_tokens` を差し込みました。
プロンプト構築・出力契約・応答検証はすべて production の経路を通っています。

| 対象                  | 入力                                                              | 条件          |
| --------------------- | ----------------------------------------------------------------- | ------------- |
| filter × 12000 / 8000 | 会話抽出後 28,526 字 / 27,810 字の 2 件を `chunkSize: 2` で束ねる | `maxRetry: 0` |
| type-category × 10000 | 会話抽出後 38,692 字の 1 件                                       | —             |
| meta × 10000          | 同上                                                              | `maxRetry: 0` |

- `temperature` は 1.0（サーバ既定と同値）/ 0.7 / 0.3 / 0.0 の 4 条件。各 10 本、温度を交互に回しました。
  0.0 は 1 本 5 分を超えるため各 3 本です
- 同一プロンプトの再送は前方一致キャッシュに載るため、2 本目以降のプロンプト処理は約 0.6 秒です。
  生成側だけを安く繰り返せます
- 暴走でスロットを占有させないため、ハーネスは常に `max_tokens: 4096` を送りました。
  1 回目の走行は `timeoutMs: 300_000` で打ち切られて応答が取れなかったため、該当 7 本はハーネスの
  タイムアウトを 900 秒に延ばして測り直しています

## 3. 結果

### 3.1 生成長（tok）

`finish_reason: length` は `max_tokens` 4096 への到達です。「空」は `{"items":[]}`（5〜6 tok）です。

| 対象                  | 1.0                                | 0.7             | 0.3                         | 0.0               |
| --------------------- | ---------------------------------- | --------------- | --------------------------- | ----------------- |
| filter × 12000        | 533〜804、要素過多 1,294 ×1、空 ×2 | 441〜946、空 ×1 | 535〜839、**暴走 4,096 ×1** | **暴走 4,096 ×3** |
| filter × 8000         | 228〜302、空 ×1                    | 214〜290、空 ×1 | 247〜321                    | 318 ×3            |
| meta × 10000          | 101〜151                           | 93〜124         | 91〜144                     | 111 ×3            |
| type-category × 10000 | 10〜20                             | 10〜20          | 10〜20                      | 20 ×3             |

出力契約の検証を通った本数（filter は要素数・ファイル名の一致を含む）は次のとおりです。

| 対象                 | 1.0   | 0.7   | 0.3   | 0.0 |
| -------------------- | ----- | ----- | ----- | --- |
| filter × 12000       | 7/10  | 9/10  | 9/10  | 0/3 |
| filter × 8000        | 9/10  | 9/10  | 10/10 | 3/3 |
| meta / type-category | 10/10 | 10/10 | 10/10 | 3/3 |

### 3.2 温度を下げても幅は縮まない

正常に終わった応答だけで比べても、生成長の幅は温度でほとんど変わりません。

- filter × 8000: 1.0 で 74 tok 幅、0.3 で 74 tok 幅
- filter × 12000: 1.0 で 271 tok 幅、0.7 で 505 tok 幅、0.3 で 304 tok 幅
- meta × 10000: 1.0 で 50 tok 幅、0.3 で 53 tok 幅

生成長を決めているのは温度ではなく、`reason` の長さと `items` の要素数です。
filter の 1 ファイルあたりの生成長は本文長とともに伸びます（8000 で約 110〜160 tok、12000 で約 220〜470 tok）。

### 3.3 暴走の中身

`length` で終わった 4 本はいずれも、1 件目・2 件目を正しく判定したあと、**判定対象ではないファイル名を
`items` に足し続けて** います。本文に他のチャットログのファイル名が含まれるログで起きる取り違えです
（`measurements-context-limits-2026-09-29.md` §5.3）。0.0（greedy）では 3 本とも同じ出力で決定的にループし、
4,096 tok の生成に 321 秒かかりました。1.0 でも 1 本が 5 要素以上を返しています（1,294 tok。ループには入らず `stop`）。

温度を下げると、この取り違えから抜け出せなくなる側に倒れます。

### 3.4 生成が止まらないとスロットが塞がる

サーバの `n_predict` は -1（無制限）です。production はクライアント側で `timeoutMs`（300 秒）に達すると
リクエストを打ち切りますが、**サーバ側の生成は継続します**（`measurements-context-limits-2026-09-29.md` §6
「踏んだ罠」と同じ挙動）。filter は `TimedOut` を再要求の対象にしないため、そのチャンクは error となり
次のチャンクへ進みます（`process-chunk.ts` は応答形式違反だけを再要求する）。ところが次のリクエストは
暴走中の生成の後ろに並び、待っている間も `timeoutMs` の計時が進みます。**1 本の暴走が後続のチャンクを
連鎖的にタイムアウトさせうる** 構造です。

`max_tokens` を送れば、暴走は上限到達で `finish_reason: length` となり、既存の分類（DR-15 / error-handling R-004 の
`ExitFailure`）でそのチャンクが error になります。判定は救えませんが、生成は上限で止まりスロットが空きます。

### 3.5 classify / normalize / review の追加実測（`cle-kju.3.3.6.1`）

DR-37 決定 5 に従い、§4 で未測定とした 3 契約を実装の子 issue `cle-kju.3.3.6.1` で同じ手順で測りました。
ハーネスは `temp/cle-kju3361/run.ts`（使い捨て、未コミット）です。production の `processChunk`（classify）・
`segmentChatlogs`（normalize）・`reviewFrontmatter`（review）をそのまま呼び、`fetchProvider` でボディに
`max_tokens: 4096`（安全弁）だけを差し込みました。**`temperature` は送っていません**（サーバ既定 1.0 = production 条件）。

| 対象      | 入力                                                                                                            | 本数 |
| --------- | --------------------------------------------------------------------------------------------------------------- | ---: |
| classify  | §2 の filter と同じ 2 件を 1 チャンクで分類（frontmatter が無いため本文先頭 500 字の経路）                      |   10 |
| normalize | 同じ 2 件を 1 回の呼び出しでセグメント分割（約 33,800 tok）                                                     |   10 |
| review    | §2 の set-frontmatter 用 1 件。type-category と meta を production 経路で 1 度埋めてから、review だけを繰り返す |   10 |

| 対象      | 正常応答の生成長（tok）          | 1 ファイルあたり最大 | 異常                                         |
| --------- | -------------------------------- | -------------------: | -------------------------------------------- |
| classify  | 172〜221（10/10）                |                  111 | なし                                         |
| normalize | 541〜1,579（production 上 8/10） |                  790 | 空配列 ×1（10 tok）、片側のファイルが欠落 ×1 |
| review    | 266〜382（8/10）                 |                    — | **暴走 4,096 ×2**（286〜319 秒）             |

- **normalize は要素過多が常態です。** production の検証を通った 8 本のうち、`items` がちょうど 2 件の応答は 2 本（541 / 598 tok）
  だけでした。残りは同じファイルの item を重複して返すか、本文に現れる別のチャットログのファイル名で item を足しています
  （§3.3 の filter と同じ取り違え）。`segmentChatlogs` は入力に無いファイルの item と 2 件目以降の重複を捨てるため、
  production ではこれらも成功として扱われます
- **review は 10 本中 2 本が暴走しました。** `errors` 配列の文字列の中で推論を書き続け、閉じないまま 4,096 tok に達しています。
  きっかけは「frontmatter に `type` / `category` が重複している」という指摘でした。`review.yaml` は `${result_yaml}` を
  title / topics / tags だけと想定していますが、`setfm-review.ts` は frontmatter 全体を渡しているため、プロンプト上で
  `type` / `category` が 2 回現れます。原因の修正は本レポートの範囲外です（別 issue）

### 3.6 review の再実測（`cle-kju.3.3.6.1.1` / `cle-kju.3.3.6.1.1.1`）

§3.5 の review の暴走について、`temp/cle-kju33611/run.ts`（使い捨て、未コミット）で同じ条件のまま測り直しました。
§3.5 との違いは、type-category と meta で埋めた frontmatter を `prepared.json` に保存し、全本数で同じ frontmatter を使った点です。

| 条件                                                                   | 本数 | 正常応答の生成長（tok） | 暴走     |
| ---------------------------------------------------------------------- | ---: | ----------------------- | -------- |
| A: 従来の user（`type` / `category` が重複）                           |   20 | 182〜617                | 4,096 ×1 |
| B: user を title / topics / tags の単一ブロックに修正                  |   20 | 126〜671                | 4,096 ×1 |
| C: B に加え、`review.yaml` に `errors` の件数上限（5）と反復禁止を追加 |   40 | 101〜328                | なし     |

- **重複は暴走の主因ではありませんでした。** A と B の暴走はどちらも、`errors` 配列にほぼ同じ違反文を書き足し続け、
  配列を閉じないまま 4,096 tok に達する形です。正常応答でも同じ違反の繰り返しが多く、`errors` は最大 15 件ありました
- C では `errors` は最大 5 件に収まり、一字一句同じ文を含む応答は 40 本中 1 本でした。判定は 40 本とも `corrected` です

## 4. 決定

決定は `decision-records.md` の **DR-37** に記録しました。

| 生成パラメータ | 決定                                                             |
| -------------- | ---------------------------------------------------------------- |
| `temperature`  | **送らない**（サーバ既定に委ねる。DR-15 のまま）                 |
| `max_tokens`   | **出力契約ごとの定数を送る**。値は暴走に対する安全弁として決める |

`max_tokens` の目安は「実測最大の 1.5 倍を 256 単位で切り上げ、下限 256」です。本レポートの実測からは次の値になります。

| 出力契約      | 実測最大（正常応答）     | 目安                                        | 上限到達までの生成時間     |
| ------------- | ------------------------ | ------------------------------------------- | -------------------------- |
| filter        | 1 ファイルあたり 473 tok | **1 ファイルあたり 768 tok × `chunkSize`**  | `chunkSize: 2` で約 120 秒 |
| meta          | 151 tok                  | **256 tok**                                 | 約 20 秒                   |
| type-category | 20 tok                   | **256 tok**                                 | 約 20 秒                   |
| classify      | 1 ファイルあたり 111 tok | **1 ファイルあたり 256 tok × ファイル数**   | 2 ファイルで約 40 秒       |
| normalize     | 1 ファイルあたり 790 tok | **1 ファイルあたり 1,280 tok × ファイル数** | 1 ファイルで約 100 秒      |
| review        | 328 tok（§3.6 の C）     | **512 tok**                                 | 約 40 秒                   |

classify / normalize / review の 3 行は §3.5 の追加実測（`cle-kju.3.3.6.1`）によります。
review は当初 §3.5 の最大 382 tok から 768 tok としていましたが、§3.6 の C の実測で 512 tok に改めました（`cle-kju.3.3.6.1.1.1.1`）。
`setup-chatlogs` は prompts ディレクトリを上書きしないため、旧 `review.yaml` を使い続ける環境では正常応答が 512 tok を
超えることがあり（§3.6 の A / B で 19 本中 2 本）、その応答は `ExitFailure` になります。旧テンプレートの利用者は更新が必要です。
normalize の「正常応答」は production の検証を通った応答とし、要素過多の応答も含めています。`items` がちょうど
ファイル数の応答だけを基準にすると 1 ファイルあたり 512 tok となりますが、その値では §3.5 で成功した 8 本のうち 4 本が
`ExitFailure` に変わります。安全弁の目的（暴走を止める）を超えて現行の成功を失敗へ変えるため採りませんでした。

ファイル数に比例させる契約（filter / classify / normalize）は、`chunkSize` ではなく **その呼び出しに実際に載せたファイル数** を
掛けます。最後のチャンクが `chunkSize` 未満のとき、上限を過大にしないためです。

`maxBodyChars` を 12000 へ上げる案は見送ります。12000 の生成長のばらつきは温度ではなく要素過多に由来し、
`max_tokens` はそれを失敗として早く返すだけで、判定を成功させるものではないためです。

## 5. 副次的な観測

- **空配列 `{"items":[]}` が温度によらず計 5 本出ました**（filter 12000 で 3 本、8000 で 2 本）。
  filter は空配列を応答形式違反として扱いリトライします（`process-chunk.ts` `_validateResponse`）
- meta と type-category は生成長が短く、時間ゲートへの影響は無視できます（最大 11 秒）

## 6. 再現手順

1. `temp/cle-kju335/sample.json`（`cle-kju.3.3.5` の層化サンプル）から、filter 用に 20k 字超の 2 件（index 3 / 7）、
   set-frontmatter 用に 1 件（index 5）を選ぶ
2. `runAI` を包む `aiRunnerProvider` を作り、`fetchProvider` でボディに `temperature` と `max_tokens` を足す。
   `usage` と `timings` は `Response.clone()` から読む
3. `/slots` の `is_processing` が false になるまで待ってから次を撃つ
4. 結果を JSONL に 1 行ずつ追記し、途中で止まっても続きから再開できるようにする

追加実測（§3.5）は `temp/cle-kju3361/run.ts` で、手順 2〜4 は同じです。`TARGETS=classify,review,normalize` で対象を選び、
`results.jsonl` から再開できます（実測中にメモリ逼迫でハーネスが停止し、normalize だけを再開して測りました）。

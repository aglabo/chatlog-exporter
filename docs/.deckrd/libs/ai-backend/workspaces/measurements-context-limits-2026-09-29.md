## Measurement Report: 入力上限（maxContentLength / chunkSize / maxBodyChars）の実測

本レポートは beads `cle-kju.3.3` / GitHub [#478](https://github.com/aglabo/chatlog-exporter/issues/478) の実測ゲートの記録です。
`2026-09-21T0254-avalon-llama-context-extension.md` §6 が「ctx 拡張の効果を実測してから決める」として
保留した入力上限を、本レポートで確定します。

**結論**: `maxContentLength` を 4000 → **10000**、`maxBodyChars` を 8000 → **10000** に引き上げます。
`chunkSize` は **2 のまま据え置き** ます。サーバ ctx が 262,144 まで伸びてもクライアント側で上限を
引き上げられる幅は ctx ではなく **プロンプト処理時間** で決まり、`timeoutMs: 300_000` / `maxRetry: 2` の
下で 1 リクエスト 180 秒に収める条件がそのまま上限になりました。

副産物として、**前方一致キャッシュが system メッセージ単位でしか効かない** ことを実測で確認しました
（§3.5）。これは `cle-kju.6`（プロンプト順序の入れ替え）の前提を崩すため、§5 に申し送ります。

---

クライアント側の関連設定は `timeoutMs: 300_000` / `maxRetry: 2` / `concurrency: 1` です。

**合格線**（`cle-kju.3` で合意、`cle-kju.5` と同じ）は次の 2 点です。

- 時間ゲート: p95 入力で 1 リクエスト **180 秒以内**。`timeoutMs` に対し 120 秒以上の余裕を残す。
  `maxRetry: 2` = 最大 3 試行のため、余裕は 1 試行あたりで確保する
- スループット上限: コーパス全体の所要が現行比 **2.0 倍** 以内

## 2. 測定内容

ハーネスは `temp/cle-kju33/` に置いた使い捨てです（コミット対象は本レポートのみ）。
プロンプトは production の生成関数をそのまま通し、送信リクエストは
`buildLlamaRequest`（`skills/_cle-libs/libs/ai/llama-request-builder.ts`）で組みました。
`timings` と `usage.prompt_tokens_details.cached_tokens` を読むため、送信だけ `fetch` を直に呼んでいます。

| 測定                   | 方法                                                        | 本数 |
| ---------------------- | ----------------------------------------------------------- | ---- |
| コーパス分布           | `ChatlogEntry` / `parseConversation` を全 3,739 件に適用    | —    |
| 本文のトークン率       | 分位点を跨ぐ 40 件の層化サンプルを `POST /tokenize`         | 40   |
| プロンプト構成         | cap 別の system / user を `POST /tokenize`                  | 49   |
| 時間ゲート             | `POST /v1/chat/completions`（cold）                         | 17   |
| 前方一致キャッシュ挙動 | 同上。固定部を揃えた連続リクエストで `cached_tokens` を見る | 8    |

## 3. 結果

### 3.1 コーパス分布（`chatlogs/originalLogs`、n = 3,739）

set-frontmatter が見るのは `entry.content`（`truncateContent` は会話抽出をしない）、
filter が見るのは会話ターン抽出後の文字列（`extractConversation`）です。両者はほぼ一致します。

| 系列            | p50   | p75    | p90    | p95    | p99     | max     | 平均   |
| --------------- | ----- | ------ | ------ | ------ | ------- | ------- | ------ |
| `entry.content` | 9,826 | 16,109 | 34,494 | 43,174 | 141,605 | 418,598 | 16,434 |
| 会話抽出後      | 9,711 | 15,989 | 34,384 | 43,064 | 141,490 | 418,483 | 16,318 |

cap ごとの切り詰め率（`entry.content` 基準 / 会話抽出後基準）は次のとおりです。

| cap        | 4000        | 8000        | 10000       | 12000       | 16000       | 20000       | 32000       |
| ---------- | ----------- | ----------- | ----------- | ----------- | ----------- | ----------- | ----------- |
| 切り詰め率 | 89.0 / 88.4 | 68.4 / 68.2 | 44.5 / 42.0 | 38.0 / 38.0 | 31.1 / 23.7 | 15.9 / 15.9 | 11.0 / 11.0 |

**本文長の中央値は 9,826 字** です。cap を 10000 に置くとちょうどここを跨ぐため、
8000 → 10000 の 1 段で切り詰め率が 68.4% → 44.5% と大きく動きます。

本文のトークン率は **0.3923 tok/char**（40 件層化サンプルの加重平均。中央値 0.361、範囲 0.279–0.488）。

### 3.2 プロンプト構成

`POST /tokenize` の実測です。「固定部」はファイルによらず同じ内容が載る部分を指します。

| 経路                             | system    | user 内の固定部 | 可変部              |
| -------------------------------- | --------- | --------------- | ------------------- |
| set-fm Phase 2.1 (type-category) | 3,398 tok | なし            | 本文のみ            |
| set-fm Phase 2.2 (meta)          | 28 tok    | **4,113 tok**   | 本文（user の末尾） |
| filter バッチ判定                | 272 tok   | ブロック枠のみ  | `chunkSize` × 本文  |

meta だけ固定部が user 側にあります。`meta.yaml` が `${topic_list}` / `${tags_list}` を
user テンプレートに埋めているためで、これが §3.5 の結果と組み合わさって効いてきます。

> **この表は 2026-09-29 の変更前の構成です。** その後 DR-36 により `meta.yaml` と
> `review.yaml` の固定部を `system` へ移しました。移動後の実測は §3.7 にあります。
> `review.yaml` はこの表に載せていませんが、変更前は system 28 tok・固定部は全量が user 側でした。

### 3.3 プロンプト処理時間モデル

プロンプト処理は入力長に対して **線形ではありません**。実測 12 点（4,993–16,498 tok）に
切片なしの 2 次を当てはめると、全点が誤差 1.58 秒以内に収まります。

```text
t(n) = 9.8437 * n + 3.518e-4 * n^2   [ms]
```

見かけの tok/s は **86.7（約 5k tok） → 63.8（約 16.5k tok）** と落ちます。
既存の「97 tok/s」「93.4 tok/s」は短いプロンプトでの値であり、**長いプロンプトの外挿に使うと楽観します**。
上限を決めるときはこのモデルを使ってください。

### 3.4 時間ゲート（cold、1 リクエストの合計秒）

対象は会話抽出後 43,064 字（p95）のファイルで、どの cap でも本文が cap 長ちょうどになります。
上限で切る経路の最悪所要は「どのファイルか」ではなく cap そのもので決まるためです。

| cap   | set-fm type-category | set-fm meta | filter (`chunkSize: 2`)   |
| ----- | -------------------- | ----------- | ------------------------- |
| 4000  | 58.9                 | 74.3        | —                         |
| 8000  | —                    | —           | 103.4                     |
| 10000 | **92.6**             | **111.1**   | **109.6 / 110.0 / 136.2** |
| 12000 | 106.2                | 126.1       | 155.4 / 165.8 / **193.8** |
| 16000 | —                    | —           | 275.2                     |
| 20000 | 159.0                | **182.3**   | 359.7                     |
| 32000 | 243.8                | 269.0       | —                         |

`chunkSize: 3` × 12000 は 324.6 秒でした。`chunkSize` × `maxBodyChars` がそのままプロンプト長になるため、
`chunkSize` を上げると時間ゲートが急速にきつくなります。

**生成時間は安定しません。** filter の `chunkSize: 2` × 12000 を 3 本撃つと、プロンプト処理は
136.4 / 134.2 / 137.0 秒とほぼ一定なのに、生成は 18.4 / 31.1 / 56.2 秒（249 / 416 / 749 tok）と振れました。
サーバの `temperature` が 1.0 で、クライアントは `max_tokens` を送らない（DR-15）ためです。
**したがって時間ゲートはプロンプト処理の余裕で判断します。**

- 10000: プロンプト処理 109 秒 → 生成側に 71 秒の余裕。3 本とも 180 秒以内
- 12000: プロンプト処理 136 秒 → 生成側に 44 秒の余裕。3 本中 1 本（193.8 秒）が超過

### 3.5 前方一致キャッシュは system メッセージ単位でしか効かない

固定部が再利用されるかどうかでスループットの見積もりが倍近く変わるため、直接測りました。

| 連続する 2 本目の内容                    | `prompt_tokens` | `cached_tokens` | プロンプト処理    |
| ---------------------------------------- | --------------- | --------------- | ----------------- |
| 同一のプロンプトを再送                   | 5,705           | **5,701**       | 67.5s → 0.6s      |
| type-category、system 同一・本文のみ相違 | 5,134           | **3,430**       | 58.1s → 23.7s     |
| meta、system 同一・本文のみ相違          | 5,848           | **68**          | 69.5s（変化なし） |

`cached_tokens` は 3 件とも **system メッセージのトークン数ちょうど**（3,430 / 68）で止まっています。
完全同一なら全量が再利用されるのでキャッシュ機構自体は動いていますが、
**user メッセージの途中までの前方一致は再利用されません。**

したがって、再利用の範囲は次のとおりです。

- type-category は system が 3,398 tok あるため、2 本目以降その分が丸ごと再利用される
- meta は system が 28 tok しかなく、固定部 4,113 tok は **毎ファイル再処理される**
- filter は system 272 tok が再利用される

### 3.6 スループット

§3.3 のモデルと §3.5 の実測キャッシュ挙動でコーパス全体（n = 3,739）を積算した値です。
キャッシュに乗る固定部は「文脈長 F から F+B まで伸ばす限界コスト」= `t(F+B) - t(F)` として扱いました。

| 対象                          | 現行              | 採用値              | 比       |
| ----------------------------- | ----------------- | ------------------- | -------- |
| set-frontmatter（2 フェーズ） | 4000 で 99.6 時間 | 10000 で 148.3 時間 | **1.49** |
| filter（`chunkSize: 2`）      | 8000 で 42.7 時間 | 10000 で 55.0 時間  | **1.29** |

本文トークン率を 0.36 / 0.3923 / 0.50 で振っても set-frontmatter 側は 1.46 / 1.49 / 1.58 で、
いずれも合格線 2.0 に十分な余裕があります。

> **この積算は meta の固定部 4,113 tok が毎ファイル再処理される前提です。** DR-36 の適用後は
> その前提が崩れ、set-frontmatter 側の値は **上振れした保守的な見積り** になります (§3.7)。
> 採用の可否は比 1.49 <= 合格線 2.0 で判断しており、実値が下がる方向の変化は決定を覆しません。
> 正確な積算には §3.3 のモデルを system / user 別に取り直す必要があり、本レポートでは行っていません。

### 3.7 固定部を system へ移した後の再実測（DR-36 適用後）

§3.5 の結論にしたがって `meta.yaml` / `review.yaml` の固定部を `system` へ移したあと、
同じ手順（§6）で測り直した値です。cache-bust の UUID 行を `system` 先頭に付け、
1 本目と 2 本目で同じ bust 文字列を使っています。

| 経路   | 連続する 2 本目           | `prompt_tokens` | `cached_tokens` | 再処理したトークン | プロンプト処理 |
| ------ | ------------------------- | --------------- | --------------- | ------------------ | -------------- |
| meta   | 1 本目（cold）            | 4,564           | 0               | 4,564              | 52.3s          |
| meta   | system 同一・本文のみ相違 | 4,567           | **4,127**       | 440                | **6.1s**       |
| review | 1 本目（cold）            | 2,632           | 0               | 2,632              | 31.1s          |
| review | system 同一・結果のみ相違 | 2,634           | **2,551**       | 83                 | **2.9s**       |

meta の `cached_tokens` は **68 → 4,127** になりました（§3.5 の変更前実測と比較）。
再処理は 440 tok（= user 側の可変部）だけに縮み、プロンプト処理は 52.3s → 6.1s です。
review も同じ形で 2,551 tok が再利用され、31.1s → 2.9s になりました。

§3.5 の「`cached_tokens` は system メッセージのトークン数ちょうどで止まる」という性質は
変更後も成り立っています。変わったのは system に載せた量だけです。

## 4. 決定

| 設定               | 変更前 | 変更後            | 拘束したゲート                                            |
| ------------------ | ------ | ----------------- | --------------------------------------------------------- |
| `maxContentLength` | 4000   | **10000**         | スループット（1.49 倍）。時間ゲートは meta 111.1 秒で余裕 |
| `maxBodyChars`     | 8000   | **10000**         | 時間ゲート（最悪 136.2 秒）。12000 は 1/3 が超過          |
| `chunkSize`        | 2      | **2**（据え置き） | 時間ゲート。上げると `chunkSize` 倍でプロンプトが伸びる   |

反映先は `.config/chatlog-exporter/config.yaml` のみで、`scripts/sync-skill-assets.sh` で
`skills/setup-chatlogs/assets/` へ同期済みです。

**組み込み既定（`DEFAULT_MAX_BODY_CHARS = 8000`、`DEFAULT_CONFIG_VALUES.maxContentLength = 4000`）は
動かしていません。** 組み込み既定を変えると config を置かない利用者の振る舞いが変わるためで、
実測値の反映先は config に限定しました。根拠は `defaults.constants.ts` の JSDoc にも記載しています。

`chunkSize: 1` へ下げれば同じ 1 リクエスト時間でより長い本文を載せられます
（固定部が 272 tok しかなく、束ねてもほとんど節約にならないため）。今回は判定の粒度を変えないことを優先し、
採りませんでした。

## 5. 未決のまま残る事項

### 5.1 `cle-kju.6`（プロンプト順序の入れ替え）は解決済み

> **解決しました（2026-09-29）。** 経緯を残すため節は削除していません。

`cle-kju.6` は `meta.yaml` の `${log_type}` / `${log_category}` を固定ブロックより後ろへ動かし、
固定部 4,113 tok を前方一致キャッシュに載せる狙いでした。§3.5 の実測どおり
**再利用は system メッセージ単位で止まる** ため、user 内で順序を変えても再利用されません。
順序の入れ替えだけでは足りませんでした。

この申し送りを受けて `meta.yaml` / `review.yaml` の固定部を `system` へ移し、
判断を **DR-36** として記録しました。移動後の実測は §3.7 にあります
（meta の `cached_tokens` 68 → 4,127、プロンプト処理 52.3s → 6.1s）。

### 5.2 生成長が安定しない

`temperature` が 1.0 で `max_tokens` を送らない（DR-15）ため、同じ入力でも生成トークン数が
249〜749 と 3 倍振れます。時間ゲートの評価をプロンプト処理の余裕で行ったのはこのためです。
生成長を抑える手当て（`temperature` の指定、出力契約での `reason` 長制限）は本 issue の範囲外です。

### 5.3 判定品質は測っていない

本レポートは所要時間とカバレッジだけを扱います。cap を上げたときに KEEP/DISCARD や
frontmatter の質が実際に改善するかは測定していません。切り詰め率の改善
（set-fm 89.0% → 44.5%、filter 68.2% → 42.0%）は入力カバレッジの指標であって品質の指標ではありません。

### 5.4 262,144 を超える実入力の往復

未実施のままです（`2026-09-21T0254-avalon-llama-context-extension.md` §7.3 と同じ）。
今回の上限では最大でも約 16,500 tok であり、ctx には 15 倍以上の余裕があります。

## 6. 再現手順

ハーネスは `temp/cle-kju33/` の使い捨てです（未コミット）。再現するときは次の順で作ります。

1. コーパス分布: `walk` で `chatlogs/originalLogs` を舐め、`ChatlogEntry` と
   `renderConversation(parseConversation(...))` で文字数を数える
2. 本文トークン率: 分位点を跨ぐ 40 件を `POST /tokenize`
3. プロンプト構成: production の `_buildTypeCategorySystemPromptForTest` / `renderPrompt` /
   `buildBatchPrompt` で cap 別の system / user を作り `POST /tokenize`
4. 時間ゲート: `buildLlamaRequest` でリクエストを組み、`POST /v1/chat/completions` を直に叩いて
   `timings` を読む。cap を超える長さのファイルを使う

### 踏んだ罠

- **キャッシュ外しに別リクエストを撃ってはならない。** `max_tokens` を送らない（DR-15）ため、
  意味のないプロンプトにモデルが 13,000 トークン以上生成し続け、`--parallel 1` の唯一のスロットを
  占有する。クライアントを kill してもサーバ側の生成は止まらず、このビルドは `--slot-save-path` 無しで
  `POST /slots/0?action=erase` も 501 のため、復旧は llama-server の再起動のみ。
  **system の先頭に UUID コメントを 1 行足す**（約 10 トークン）方式を使う
- **`/slots` の `is_processing` を見て空くまで待つ。** 途中で throw すると数十分の掃き出しが
  最初からやり直しになる
- **キャッシュの検証で 1 本目だけ cache-bust してはならない。** 2 本目が 1 本目の prefix と
  一致しなくなり、`cached_tokens` が 0 に見える。1 本目・2 本目で同じ bust 文字列を使い、
  差分を測りたい箇所だけに限定する。この取り違えで §3.5 を一度読み違えた
- **分位点の選定に `ChatlogEntry` を全件作らない**…ではなく、**作ってよい**。
  保持せず数値だけ拾えば 3,739 件の走査が 26 秒で終わる。前回「数分かかって実質固まる」と記録されたのは
  エントリを配列に溜めたためと見られる

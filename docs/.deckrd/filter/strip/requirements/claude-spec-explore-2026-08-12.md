## 1. 網羅性 (Completeness)

### F-01: frontmatter の有無を判定する規則が Section 4.2 に無い

> 対象版: spec v1.0.0 ／ 状況: 解消済み。R-002 を新設し Edge 15 を error へ変更 (DR-09)

#### 所見

Edge 15 は「frontmatter を持たない」ファイルを passthrough と分類しています。
また REQ-F-001 の GIVEN は「対象ファイルが frontmatter を持ち」を除去の前提条件としています。

しかし Section 4.2 の R-002 〜 R-007 に frontmatter の有無を検査する規則がありません。
frontmatter を持たず定型部マーカーを持つファイルを考えます。
このファイルは R-002 〜 R-006 のいずれにも該当せず、R-007 により stripped と分類されます。
これは Edge 15 と矛盾します。

#### 影響

frontmatter 無しのファイルには処理済みマーカーの付与先がありません。
その状態のまま書き込みへ進む恐れがあります。

#### 検討候補

- R-004 の前段に「frontmatter を持たない → passthrough」の規則を追加してはどうでしょうか
- あるいは Edge 15 の分類を見直し、frontmatter 無しを error とする案も考えられます。
  実測データでは frontmatter が全件に存在するため、異常入力として扱う余地があります

### F-02: R-002 の順序根拠が DR-08 の一括削除と整合しない

> 対象版: spec v1.0.0 ／ 状況: 解消済み。順序根拠が R-010 の一括削除を参照する記述に更新済み

#### 所見

R-002 (処理済みマーカーによる skipped) を R-003 (退避の存在による skipped) より先に置く根拠として、
仕様書は次のように記しています。

> 退避のみを根拠にすると、R-009 による削除後の再実行で strip 済みファイルが再処理されます。

この根拠は DR-06 (当該実行が作成した退避のみを削除) を前提としたものです。
DR-08 により削除が対象ディレクトリ配下の一括操作となったため、
削除される退避の範囲が広がっています。

順序そのものは依然として妥当ですが、根拠の記述が旧決定を参照したままです。

#### 影響

規則の正しさには影響しませんが、将来 R-002 / R-003 の順序を見直す際に
誤った前提で判断される恐れがあります。

#### 検討候補

- 根拠の記述を DR-08 の削除範囲に合わせて更新してはどうでしょうか

### F-03: 退避削除自体が失敗した場合の扱いが未定義である

> 対象版: spec v1.0.0 ／ 状況: 未解消。F-07 として再掲

#### 所見

R-009 は削除の実行を定めますが、削除操作そのものが失敗した場合
(ファイルロック・権限・アンチウイルスによる占有など) の扱いを規定していません。

Section 3.2 の結果分類は入力ファイル単位の分類であり、
削除フェーズの失敗を表現する分類がありません。

requirements 側でも REQ-F-006 のサマリー項目に「`.bak` の削除有無 (削除件数、または保持理由)」とあり、
部分的な削除失敗を報告する形式が定まっていません。

#### 影響

Windows 環境では `Deno.remove` が一時的に失敗する事象が想定されます。
6000 件規模の一括削除では、一部失敗が現実的に起こりえます。

#### 検討候補

- 削除失敗を warning として報告し、終了コードには影響させない案
- 削除失敗件数をサマリーに含める案
- codex レビュー (`codex-req-risk-2026-08-12.md` 経路 5) でも同種の指摘が「未」のまま残っています

### F-04: dry-run 時の分類が実行時と一致する保証が未記載である

> 対象版: spec v1.0.0 ／ 状況: 未解消

#### 所見

Section 3.2 は「分類そのものは通常実行と同一の規則で決定します」と記しています。

ただし R-003 (退避の存在) と R-002 (処理済みマーカー) は、
直前に処理したファイルの副作用に依存しません。
一方で dry-run は退避とマーカーのいずれも作成しません。
そのため同一ディレクトリを続けて 2 回 dry-run しても結果は変わりません。

これは望ましい性質ですが、仕様書に「dry-run は冪等である」旨の明示がありません。

#### 影響

実装時に dry-run の分類ロジックを別経路で実装する誘因が生じ、
本番実行との乖離を招く恐れがあります。

#### 検討候補

- 「分類は副作用と独立に決定され、dry-run と通常実行で同一の結果を返す」旨を
  Section 3.2 に補足してはどうでしょうか

### F-05: `backupPath` の `null` 戻り値が R-004 により到達不能になっている

> 対象版: spec v1.1.0 ／ 状況: 未解消

#### 所見

DR-03 の決定 2 は `backupPath` の挙動を次のように定めています。

> `backupPath` は `.bak` が既に存在する場合、退避せず `null` を返します。
> これにより REQ-F-010 の「当該実行で作成した `.bak` のみ削除」が自然に成立します。

しかし Section 4.2 の R-004 は「対応する退避ファイルが既に存在する」ファイルを
`skipped` として分類し、書き込み経路に進ませません。
退避付き書き込み (R-009) に到達するのは R-008 が成立したファイルのみです。

したがって `backupPath` が呼ばれる時点で `.bak` は存在せず、`null` を返す分岐に到達しません。

あわせて、`null` の存在理由として「当該実行で作成した `.bak` のみ削除」が記されています。
この REQ-F-010 の条件は、DR-08 により対象ディレクトリ単位の一括削除へ変更されました。
したがって現在は存在しません。DR-03 の補足もこの点を認めています。

#### 影響

仕様の正しさには影響しません。R-004 が先に作用するため、二重退避は発生しません。

ただし到達しない分岐が仕様に残ると、実装時に次の 2 つの誘因が生じます。

- 到達不能な分岐に対するテストケースを書こうとして、R-004 を迂回する経路を作る
- `null` 戻り値を冪等判定の材料と誤解し、DR-03 の決定 3 (冪等判定は呼び出し側に置く) と
  重複した判定を Provider 側に持ち込む

#### 検討候補

- `backupPath` の戻り値を `Promise<string>` に単純化する案が考えられます
- あるいは `null` を「防御的な二重化であり通常は到達しない」と位置づけ、
  その旨を明示する案も考えられます
- いずれにせよ `null` の根拠として REQ-F-010 の旧条件を引く記述は、
  更新の余地があるように見えます

### F-06: R-002 新設に伴い REQ-F-003 と R-005 の対応関係がずれている

> 対象版: spec v1.1.0 ／ 状況: 未解消。DR-09 の Consequences に記録済み

#### 所見

Section 6 の Traceability は REQ-F-003 を `R-005, Edge 2` に対応づけています。

REQ-F-003 の GIVEN は「対象ファイルが本文に `## Summary` 見出しを 1 つも含まない」であり、
R-005 の条件と一致します。この対応自体は妥当です。

一方 REQ-F-003 の NOT DO には「ファイル内容を変更する、または `.bak` を作成する」とあり、
AC-004 は「`.bak` ファイルが作成されていない」ことを検証項目に含めています。

しかし v1.1.0 では R-002 (frontmatter を持たない → error) が新設されました。
frontmatter を持たず `## Summary` も持たないファイルは、R-005 より先に error と分類されます。
このファイルは REQ-F-003 の GIVEN を満たしますが、passthrough ではなく error になります。

#### 影響

実害は限定的です。いずれの分類でも内容は変更されず `.bak` も作成されないため、
REQ-F-003 の NOT DO は満たされます。

ただし AC-004 のシナリオ「`## Summary` を含まないファイル」に
frontmatter を持たない検体を用いた場合、期待値は passthrough ではなく error になります。
テスト設計時に検体の前提が明示されていないと、想定と異なる分類で失敗します。

#### 検討候補

- AC-004 の Given に「frontmatter を持つ」を補う案が考えられます
- あるいは Section 6 の REQ-F-003 の Notes に、R-002 が先行する旨を添える案も考えられます

### F-07: 退避削除失敗時の扱いが未定義のまま残っている

> 対象版: spec v1.1.0 ／ 状況: 未解消。F-03 の再掲

#### 所見

1 回目のレビューの F-03 と同一の論点です。v1.1.0 では変更されていません。

R-010 は削除の実行を定めますが、削除操作そのものが失敗した場合の扱いを規定していません。
Section 3.2 の結果分類は入力ファイル単位の分類であり、削除フェーズの失敗を表現する分類がありません。

codex レビュー (`codex-req-risk-2026-08-12.md` 経路 5) でも同種の指摘が未解決のまま残っています。

#### 影響

Windows 環境では `Deno.remove` の一時的な失敗 (ファイルロック・アンチウイルスによる占有) が
想定されます。6000 件規模の一括削除では一部失敗が現実的に起こりえます。

R-010 は「一括削除」を定め、Section 4.3 は逐次削除を「一部だけ削除済み」の状態を理由に
退けていますが、一括削除の途中失敗でも同じ状態が生じます。

#### 検討候補

- 削除失敗を warning として報告し、終了コードには影響させない案
- 削除失敗件数をサマリーに含める案
- requirements 側の決定を要するため、`/deckrd review req --phase harden` の対象候補です

## 2. 曖昧さ (Ambiguity)

### A-01: 「除去率」の定義が無い

> 対象版: spec v1.0.0 ／ 状況: 解消済み。除去率の算出式を Section 4.2 に追加

#### 所見

R-006 と Edge 6 は「除去率が 99% を超える」を error の条件としています。
しかし除去率の算出式は、仕様書と requirements のいずれにも定義がありません。

少なくとも次の解釈が可能です。

| 解釈 | 分母                                | 分子         |
| ---- | ----------------------------------- | ------------ |
| (a)  | ファイル全体のバイト数              | 除去バイト数 |
| (b)  | 本文のバイト数 (frontmatter を除く) | 除去バイト数 |
| (c)  | 本文の行数                          | 除去行数     |

frontmatter を分母に含めるか否かで、境界付近のファイルの判定が変わります。
また「実測平均は 77.8%」という記述は requirements の DR-01 根拠に由来します。
そこでの 77.8% は「定型部がファイルサイズに占める割合」であり、解釈 (a) に近いものです。

#### 影響

閾値 99% は安全弁であり、解釈の違いが誤検出・検出漏れに直結します。

#### 検討候補

- 除去率の定義を Section 3 または Section 4 に明記してはどうでしょうか
- 実測値 77.8% との整合を保つ観点では、解釈 (a) が自然に見えます

### A-02: 「対象ディレクトリ配下」が再帰的かどうか不明である

> 対象版: spec v1.0.0 ／ 状況: 未解消。P-04 として再掲

#### 所見

R-009 は削除範囲を「対象ディレクトリ配下の退避ファイル全件」と記します。

一方 Section 2.2 の前提では、走査は `*.md` を対象とすると述べられています。
ファイル走査は再帰的である旨が調査で確認されていますが、
仕様書本文には再帰性の記述がありません。

削除が再帰的か否かで、`<agent>/<YYYY>/<YYYY-MM>` 配下にサブディレクトリが存在した場合の
挙動が変わります。

#### 影響

現状の `originalLogs/` 構造にサブディレクトリは存在しないため、実害はありません。
ただし構造が変わった場合、想定外のファイルまで削除される恐れがあります。

#### 検討候補

- 削除範囲の再帰性を明記してはどうでしょうか
- 走査範囲と削除範囲を同一と定義すると、両者のずれを防げます

### A-03: 「処理済みマーカー」と「定型部マーカー」の語が近接している

> 対象版: spec v1.0.0 ／ 状況: 未解消

#### 所見

仕様書では次の 2 つをいずれも「マーカー」と呼んでいます。

- 処理済みマーカー = frontmatter の `_status: stripped` (R-002)
- 定型部マーカー = 本文中の `## TOPICS ASSIGNMENT RULES` (R-005)

R-002 と R-005 は判定順序が離れており文脈で区別できますが、
Section 4.2 の順序根拠の記述では両者が同一段落に現れる箇所があります。

#### 影響

読み手が取り違えると、判定順序の理解を誤る恐れがあります。

#### 検討候補

- 用語集を Section 3 に設けるか、いずれかの呼称を変更してはどうでしょうか

### A-04: R-007 の「除去後の本文」が R-002 の error 条件と重複しうる

> 対象版: spec v1.1.0 ／ 状況: 未解消

#### 所見

R-007 の条件は「除去後の本文が空である、または除去率が 99% を超える」です。

一方 REQ-F-008 の判定基準は 3 点を挙げています。

- frontmatter を持たない
- 除去後の本文が空、または `## Summary` 以降が存在しない
- 除去率が 99% を超える

このうち「`## Summary` 以降が存在しない」に対応する規則が Section 4.2 に見当たりません。
R-005 は「`## Summary` が 1 つも存在しない」を passthrough としますが、
これは除去前の判定であり、REQ-F-008 が挙げる除去後の条件とは別物です。

`## Summary` が存在する以上、除去範囲は「先頭から最初の `## Summary` 直前まで」であり、
除去後の本文は必ず `## Summary` から始まります。
したがって「除去後に `## Summary` 以降が存在しない」は構造的に起こらないようにも読めます。

#### 影響

REQ-F-008 の 3 基準のうち 1 つが spec 側の規則に現れません。
Traceability 上は REQ-F-008 → R-002, R-007 で網羅されているように見えます。
しかし実際には 1 基準が落ちている可能性があります。

安全弁の条件が 1 つ欠けると、想定外の入力に対する保護が弱まります。

#### 検討候補

- 「`## Summary` 以降が存在しない」が構造的に到達不能であることを確認し、
  到達不能であれば REQ-F-008 側から削除する案が考えられます
- 到達しうる経路がある場合は、R-007 の条件に明示的に加える案が考えられます

### A-05: Edge 14 の分類表記 `stripped→skipped` が単一実行の結果と読めない

> 対象版: spec v1.1.0 ／ 状況: 未解消

#### 所見

Section 5 の Edge 14 は Classification 欄に `stripped→skipped` と記しています。

他の 14 件はいずれも単一の分類値 (stripped / passthrough / skipped / error / 実行拒否) です。
Edge 14 のみが 2 つの値を矢印で結んでいます。

意味としては「1 回目の実行で stripped、2 回目の実行で skipped」と読めます。
一方 Section 3.2 は「各入力ファイルは相互に排他的な 4 つの結果のいずれかに分類されます」と定めます。
そのため単一実行の結果を表す欄に 2 値が入るのは、表記の不統一に見えます。

#### 影響

読み手が「1 回の実行内で分類が遷移する」と誤解する恐れがあります。
実際には R-003 により、2 回目の実行で独立に skipped と判定されます。

#### 検討候補

- Classification を `stripped` (初回) とし、Rationale 側に再実行時の挙動を記す案
- あるいは実行回を明示する列を追加する案が考えられます

## 3. 代替案 (Alternatives)

### O-01: 安全弁の閾値を固定値以外とする案

> 対象版: spec v1.0.0 ／ 状況: 未決。Section 7 の確認事項 3 として継続

#### 所見

Section 7 の確認事項 3 にも挙がっていますが、代替案を整理しておきます。

| 案 | 内容                       | 利点                             | 欠点                              |
| -- | -------------------------- | -------------------------------- | --------------------------------- |
| A  | 固定値 99% (現案)          | 単純・設定不要                   | 想定外の形式で誤検出しうる        |
| B  | オプションで上書き可能     | 例外的なデータに対応できる       | 安全弁を無効化する経路が生まれる  |
| C  | 除去後の絶対バイト数も併用 | 極端に小さいファイルを保護できる | 閾値が 2 つになり判定が複雑化する |

案 C は「除去後の本文が空」という既存条件の一般化にあたり、
現在の 2 条件 (空・99% 超) の中間を埋めます。

### O-02: 退避削除を明示オプションとする案

> 対象版: spec v1.0.0 ／ 状況: 記録のみ

#### 所見

DR-06 の Alternatives で codex が提案し不採用となった案ですが、
DR-08 で削除範囲が広がったことにより、判断の前提が一部変わっています。

現在は「対象ディレクトリ配下の全 `.bak`」が削除対象であり、
前回中断で残った退避も含まれます。
この範囲拡大は DR-08 の Consequences に Negative として記録済みです。

再検討を促すものではありません。
ただし範囲が広がった事実は、不採用理由の再確認に値します。

### O-03: R-002 を実行前チェックとして前倒しする案

> 対象版: spec v1.1.0 ／ 状況: 記録のみ。DR-09 で Option C として不採用

#### 所見

R-002 (frontmatter を持たない → error) はファイル単位の規則として
Section 4.2 の先頭に置かれています。

実測では `originalLogs/` の全ファイルが frontmatter を持ちます。
そのため R-002 に該当するファイルが 1 件でも見つかった時点で、
パイプラインの前提が破れていることが判明します。

| 案 | 内容                                             | 利点                                       | 欠点                                             |
| -- | ------------------------------------------------ | ------------------------------------------ | ------------------------------------------------ |
| A  | ファイル単位で error 計上し継続 (現案)           | DD-03 と整合し、1 件の異常で全件を止めない | 前提破れの検出が実行終了時まで分からない         |
| B  | 走査時に全件を先に検査し、1 件でもあれば実行拒否 | 破壊的処理の前に前提破れを検出できる       | R-001 以外の実行拒否経路が増え、判定が複雑化する |
| C  | error 件数が閾値を超えた時点で中断               | 大量の前提破れを早期に検出できる           | 閾値の根拠が新たに必要になる                     |

現案 A は DD-03 に基づく一貫した選択であり、変更を促すものではありません。
DD-03 では、安全弁を個別ファイル単位で作用させ、実行全体を中断しないと定めています。

ただし R-002 が他の error 条件 (R-007) と性質を異にする点は、記録に値します。
R-007 は「当該ファイル固有の異常」ですが、R-002 は「パイプライン全体の前提破れ」を
示唆するものであり、Section 5 の Edge 15 もその旨を記しています。

## 4. 前提 (Assumptions)

### P-01: 並行実行を想定しない前提の帰結が未記載である

> 対象版: spec v1.0.0 ／ 状況: 未解消

#### 所見

Section 3.1 の Assumptions に「同一ファイルに対する並行実行は想定しません」とあります。

一方 R-008 の 3 段階順序は中断耐性を担保する設計であり、
中断 (クラッシュ・強制終了) は想定していることが読み取れます。

「並行実行は想定しない」と「中断は想定する」の線引きは妥当ですが、
前者が満たされなかった場合の帰結が記されていません。

#### 検討候補

- 並行実行時に何が壊れうるかを一文添えると、前提の重要性が伝わりやすくなります
  (例: 同一ファイルへの同時書き込みで退避が失われる可能性)

### P-02: 実測データの標本サイズが前提ごとに異なる

#### 所見

Section 2.2 の前提表と REQ-C-004 / REQ-C-008 により、

#### 検討候補

### P-03: 退避ファイルが走査対象に混入しない根拠が実装に依存している

> 対象版: spec v1.1.0 ／ 状況: 未解消

#### 所見

Section 2.2 は「退避ファイルと一時ファイルは走査対象に混入しない」前提について、
根拠を「走査は `*.md` を対象とし、拡張子が一致しない」と記しています。

この前提は本レビューで実装を確認し、成立することを検証しました。
`findFiles` は `${dir}/*${ext}` のグロブを用います (`_cle-libs/libs/file-ops/find-files.ts`)。
そのため `ext` が `.md` のとき、`<name>.md.bak` および `<name>.md.tmp` は一致しません。

ただし仕様書の記述は前提の妥当性のみを述べ、それが `findFiles` のグロブ実装に
依存している点を明示していません。

#### 影響

`findFiles` の `ext` フィルタがグロブから拡張子の部分一致等に変更された場合、
`.bak` が走査対象に入り、退避に対して strip が適用される恐れがあります。

この経路が生じると、R-004 (退避が存在すれば skipped) は `<name>.md.bak.bak` の
有無を見ることになり、保護が働きません。

#### 検討候補

- 前提の根拠に依存先 (`findFiles` のグロブ方式) を明記してはどうでしょうか
- 走査結果から退避・一時ファイルを明示的に除外する規則を設ける案も考えられます

  ---

### P-04: R-010 の再帰性が未記載のまま残っている

> 対象版: spec v1.1.0 ／ 状況: 未解消。A-02 の再掲

#### 所見

1 回目のレビューの A-02 と同一の論点です。v1.1.0 では変更されていません。

R-010 は削除範囲を「対象ディレクトリ配下の退避ファイル全件」と記しますが、
再帰的か否かの記述がありません。

本レビューで確認したところ、`findFiles` はキューを用いてサブディレクトリを再帰的に走査します。
走査が再帰的である以上、削除範囲を走査範囲と一致させるならば削除も再帰的になります。

#### 影響

現状の `originalLogs/<agent>/<YYYY>/<YYYY-MM>` 構造にサブディレクトリは存在しないため、
実害はありません。構造が変わった場合に想定外のファイルまで削除される恐れがあります。

#### 検討候補

- 削除範囲の再帰性を明記してはどうでしょうか
- 走査範囲と削除範囲を同一と定義すると、両者のずれを防げます

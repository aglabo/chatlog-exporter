## 危険な前提 3 つ

### 1. `error 0` を「`.bak` を削除してよい」根拠とみなしている（最重要）

**判定: 済**（DR-06 で対応）

`error 0` は「実装が例外を出さなかった」だけで、「除去範囲が正しかった」保証ではない。
境界判定やマーカー判定に **系統的なバグ** があれば、全ファイルを誤変換してから
唯一の復旧手段（`.bak`）を消せる。

対象は REQ-F-010 です。

> **決着（DR-06 / requirements v1.7.0）**:
>
> 1. 削除条件を `_status` 基準に変更しました。「例外が出なかったか」ではなく
>    「全ファイルの `_status` が `stripped` か」を条件とし、処理結果に直接紐づけています。
> 2. 指摘の前提が誤りであることが判明しました。「`.bak` が唯一の復旧手段」という前提は成立しません。
>    `originalLogs/` は一次ソースではなく `export-chatlogs` による派生物であり、
>    一次ソースは `~/.claude/projects/` の JSONL
>    （`claude-exporter.ts:215`）。`writeSession`（`session-writer.ts:90`）は
>    `Deno.writeTextFile` で **無条件上書き** するため、re-export で復元できる。
>    したがって **復旧不能という事態は起きない**。
>
> この前提の訂正により、codex の提案（既定無効化 / manifest + 別コマンド）は
> 過剰と判断し不採用とした。詳細は DR-06 の Rationale を参照。
>
> **残存リスク（DR-06 Negative に記録済み）**: re-export は全セッションの再変換を伴い
> 時間コストが大きい。また `~/.claude/projects/` から元セッションが削除されている場合は機能しない。

### 2. claude/2026-07 の実測を運用時の安全性の根拠として扱っている

判定: 済（v1.8.0 で解決）

Q-04 で他 agent / 他年月の未測定を認めているが、実装上の強制条件としては弱い。

> **決着済みの部分**: Q-04 は v1.4.1 で解決済み。codex 42 件・chatgpt 9 件を実測し
> 定型部マーカー保有 0 件を確認。既存 `filter` が定型プロンプトファイルを削除済みであることが原因と判明。
> REQ-C-004 に検査結果と再検査条件を記載済み。
> 再検査の条件は、`set-frontmatter` のテンプレートまたは `filter` の削除パターンが変更された場合です。
>
> **残る論点**: REQ-C-004 は「未検証データセットには適用してはならない」と規定するが、
> **実行時にそれを強制する仕組みがない**。運用上の注意に留まっている。
>
> **v1.8.0 での決着**: 軸ごとに切り分けたうえで、残る 2 経路を実行時拒否として規範化した。
>
> - agent 軸について、指摘は成立しません。agent は常に単一値へ解決され
>   （`DEFAULT_FILTER_CONFIG.agent` / `DEFAULT_AGENT`）、全エージェントを走査する経路が存在しません。
>   実測結果に加えて仕様上も分離が保証される旨を REQ-C-004 に明記しました。
> - period の不正形式は既存実装で拒否済みです。agent の次の位置引数は `YYYY-MM` 形式が必須で、
>   違反時は `InvalidPeriodPosition` を throw します（`parse-args.ts`）。
> - period の省略と `--input-dir` override は、ここだけが実際に破れます。
>   前者は `agentPath()` が agent のみを返し全年月が再帰走査され、
>   後者は agent / period がともに無視されます（`resolve-directory.ts`）。
>   この 2 経路を REQ-C-008 で実行時拒否とし、受理範囲を実測済みの `<agent> <YYYY-MM>` に限定しました
>   （AC-021 / AC-022）。
>
> あわせて Q-04 を (a) 他エージェント = 解決 / (b) 他年月 = 未実測のまま適用範囲外へ封じる、に分離した。

対象は REQ-C-004 / REQ-C-008 / Q-04 です。

### 3. `_status` が永続的な冪等性マーカーとして信頼できるという前提

判定は「部分」です。

> **決着済みの部分**:
>
> - 冪等性そのものは REQ-F-009 の判定順序 1（`_status: stripped` があれば `.bak` の有無によらず skipped）で確保済み。
>   `.bak` 削除後も frontmatter は残るため、REQ-F-010 との組み合わせでも成立する。
> - `toFrontmatter()` の `fieldOrder` 誤りによる未知フィールド消失は、
>   **REQ-C-005 として規範化済み**（v1.5.0、AC-018 で検証）。
>
> **残る論点**: `_status` は単一値（後勝ち）のため、後続処理が上書きすると strip の記録が失われる。
> DR-04 の Negative に「他スキルが使い始める際は上書き規則の決定が必要（将来の DR 対象）」と記録済み。
> 現時点では strip のみが `_status` を書くため実害はない。

対象は REQ-F-009 / DR-04 / REQ-C-005 です。

### 不採用とした Codex の提案

> `.bak` 自動削除を既定無効にして、`--delete-backups-on-success` のような明示フラグ
> または manifest 検証後の別コマンドに分ける。

**不採用**（DR-06）。この提案は「復旧不能になる」という前提に立っています。
しかし一次ソース（`~/.claude/projects/`）からの re-export で復元できるため、前提が成立しません。
既定無効化では 6000 件規模で `.bak` が残り続け、ディスク使用量は倍増したままになります。
manifest 方式は追加の設計・実装・検証コストを伴います。
復旧不能でない以上、いずれも過剰と判断しました。

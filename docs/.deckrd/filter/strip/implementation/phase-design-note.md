## 1. フェーズ分割の方針

### 1.1 なぜ 8 ユニットと 1 対 1 にしないか

specifications.md Section 2.3 は機能を 8 ユニットに分解しています。
しかしフェーズ境界をユニット境界と一致させることはできません。

決定的な理由は **安全弁ユニット** にあります。
安全弁が担うのは R-002 と R-007 ですが、この 2 つは同一の判定カスケードの
step 1 と step 6 に分かれて位置します (Section 4.2) 。
仕様は「順序の変更は許されません」と定めるため、
安全弁を独立したフェーズに切り出すと、順序が壊れるか、カスケードが二重化します。

同じ理由が境界検出ユニットにも当てはまります。
境界検出の結果 (最初の `## Summary` とマーカーの位置) は R-005 / R-006 の判定材料であり、
判定と分離すると同じ走査を 2 回行うことになります。

したがってフェーズ境界は **判定と副作用** で切ります。
これは DR-15 で spec に追記した「分類ロジックは単一の判定関数に閉じなければならず、
副作用の有無のみを呼び出し側で分岐しなければならない」という規定とも一致します。

### 1.2 ユニット → フェーズ対応

| Unit (spec 2.3)  | Phase           | 備考                                      |
| ---------------- | --------------- | ----------------------------------------- |
| 引数受理ゲート   | Phase 0         | 1 対 1                                    |
| (列挙・読み込み) | Phase 1         | spec 2.3 に対応ユニット無し (下記参照)    |
| 境界検出         | Phase 2 の内部  | 判定の材料であり、単独では観測されない    |
| 分類             | Phase 2         | R-002 〜 R-008 のカスケード全体           |
| 安全弁           | Phase 2 の内部  | R-002 / R-007。カスケードの一部として作用 |
| 退避付き書き込み | Phase 3 / 4 / 5 | REQ-NF-005 の 3 段階に分割 (下記参照)     |
| 処理済み記録     | Phase 5         | 差し替えの成立と同時に記録します          |
| 退避削除         | Phase 6         | 1 対 1。実行単位の後処理                  |
| 結果報告         | Phase 7         | 1 対 1                                    |

Phase 1 は spec 2.3 のユニット一覧に対応項目がありません。
Section 3.1 が入力を「対象ディレクトリ配下の `*.md`」と定めるため列挙は必須ですが、
2.3 は判断を伴う処理のみを列挙しており、列挙・読み込みを含めていません。
実装上は必要であるため、フェーズとしては独立させます。

### 1.3 退避付き書き込みを 3 フェーズに分ける理由

REQ-NF-005 は退避付き書き込みを **3 段階の操作順序** として規定します。
REQ-NF-004 は一時ファイル経由による原子性を要求します。

この 3 段階はいずれも独立して失敗しえます。
一時ファイルの書き出しに失敗した場合は退避へ進んではならず、
退避に成功しても差し替えに失敗すれば `<name>.md` が存在しない状態が残ります。

順序は「一時ファイル書き出し → 退避 → 差し替え」であり、退避が先ではありません (REQ-NF-005) 。
先に書き出すことで、書き込み中の中断が本体を破壊しません (REQ-NF-004) 。

段階を 1 フェーズに潰すと、中断がどの段階で起きたかを実行後に判別できません。
差し替えは中断耐性の要となる操作であるため、独立して観測できる形にします。

処理済み記録を Phase 5 に置くのは、差し替えの成立が処理済みの唯一の根拠であるためです。
一時ファイルの作成のみで記録した場合、差し替えに失敗したファイルが
次回実行で `done` と判定され、strip されないまま残ります。

## 2. フェーズ構成

```text
Phase 0  受理ゲート            R-001            ← 列挙より前
   |  受理
   v
Phase 1  一覧取得・キャッシュ  (規則なし)
   |
   v
Phase 2  判定                  R-002 〜 R-008   ← 純粋・dry-run と共通
   |
   +-- stripped --> Phase 3  strip 済みログ作成 R-009 (1/3)  ┐
   |                   |                        (.md.tmp)      |
   |                   v                                      | dry-run
   |                Phase 4  退避作成           R-009 (2/3)  | では
   |                   |                        (.md → .bak)   | 呼ばない
   |                   v                                      |
   |                Phase 5  本番ログへ差し替え R-009 (3/3)  |
   |                   |                        (.tmp → .md)   |
   |                   |                        + キャッシュ記録
   +-- done -----------+                                      |
   +-- passthrough ----+                                      |
   +-- error ----------+                                      |
                       v                                      |
                Phase 6  退避削除               R-010〜R-013 ┘
                       |                        (error 0 件 + 包含成立時のみ)
                       v
                Phase 7  結果報告               (集計)
```

### Phase 0: 受理ゲート

**規則**: R-001

年月の省略、または入力ディレクトリ override の指定を検出し、実行を拒否します。

**列挙より前に評価しなければなりません** (Section 4.2) 。
列挙後に拒否した場合、未検証範囲のファイル一覧が出力に現れ、拒否の意味が失われます。

検査は共通の引数解析ではなく strip 側で行います (DD-04) 。
`filter` / `noise-filter` の既存挙動を変更しないためです。

### Phase 1: 一覧取得・キャッシュ読み込み

**規則**: N/A

対象ディレクトリ配下の `*.md` を列挙し、各ファイルを読み込みます。
あわせて `ChatlogCache` を初期化します (`await cache.ready`) 。

退避ファイルと一時ファイルは拡張子が一致しないため、走査結果に含まれません (Section 3.1) 。

読み込み失敗は Phase 2 の判定対象から分離します。
`loadFilterEntries` が `{ entries, errors }` を返す既存パターンに倣います。

**本フェーズは Phase 0 の後に置かなければなりません。**
R-001 は列挙より前に評価する必要があるためです (Section 4.2) 。
列挙を先に行うと、拒否されるべき実行でも未検証範囲のファイル一覧が出力に現れ、
拒否の意味が失われます。

### Phase 2: 判定

**規則**: R-002 〜 R-008 (7 規則)

本フェーズが本設計の中核です。

**単一の純粋関数** として実装し、ファイルごとに次を返します。

```text
{ outcome, reason, removalStartLine, removalEndLine, removedBytes }
```

- `outcome` — stripped / done / passthrough / error の 4 分類 (DR-15)
- `reason` — 該当した規則 ID。REQ-F-005 が求める dry-run の「判定理由」に対応
- `removalStartLine` / `removalEndLine` — 除去の開始行と終了行
- `removedBytes` — 除去バイト数。R-007 の除去率算出にも用いる

開始行と終了行を分けて保持するのは、REQ-F-005 が dry-run 出力に
「除去対象となる行範囲」を求めるためです。
範囲を単一の値として持つと、報告時に再計算が必要になります。

除去範囲は常に本文先頭から最初の `## Summary` 直前までであるため (DR-01) 、
開始行は本文先頭に固定されます。
それでも開始行を明示的に返すのは、frontmatter の行数だけ本文がずれるためです。
報告される行番号はファイル全体を基準とします。

境界検出と安全弁は本関数の内部に閉じます (1.1 参照) 。

**dry-run と通常実行でバイト単位に同一の経路を通ります。**
副作用を一切持たないため、モードによる分岐が不要です。
これはレビュー指摘 F-04 への対応であり、
分類を dry-run 専用経路で実装した場合に生じる通常実行との乖離を構造的に防ぎます。

R-007 の判定には除去範囲の確定が必要なため、
dry-run であっても除去範囲とバイト数を実際に計算します。
計算しない場合、R-007 の判定と REQ-F-005 のバイト数報告がいずれも成立しません。

### Phase 3: strip 済みログ作成 (一時ファイル)

**規則**: R-009 (3 段階の 1 段目)

`outcome === stripped` のファイルのみを対象とします。

Phase 2 が返した除去範囲に基づき、除去後の内容を
**一時ファイル `<name>.md.tmp`** へ書き出します (REQ-NF-004 / REQ-NF-005 手順 1) 。

この段階では本体およびバックアップを作成しません。
書き込み中に中断しても `<name>.md` は無傷です。

frontmatter は変更しません (DR-14) 。
`_status` を含むいかなるフィールドも付与・変更してはなりません。
AC-024 が「strip 済みファイルの frontmatter が strip 前と同一である」ことを求めます。
判定は `ChatlogFrontmatter` による同一性比較で行います (バイト単位ではありません) 。
`writeTextFile` が `normalizeLine` を適用するため、CRLF 入力では改行が LF へ正規化されるためです。

**dry-run では本フェーズを実行しません。**

### Phase 4: 退避作成

**規則**: R-009 (3 段階の 2 段目)

元ファイル `<name>.md` を `<name>.md.bak` へ **リネーム** します (REQ-NF-005 手順 2) 。

コピーではなくリネームです。
この時点で `<name>.md` は一時的に存在しなくなります。
手順 2 と 3 の間で中断した場合、`<name>.md.bak` に元の内容が残るため復元可能です。

`BackupProvider` および `backupToBak` は未実装であり、本フェーズの実装時に新設します (DR-17) 。
既存 `.bak` がある場合、`backupToBak` はリネームをスキップし `null` を返します。

**dry-run では本フェーズを実行しません。**

### Phase 5: 本番ログへ差し替え

**規則**: R-009 (3 段階の 3 段目)

一時ファイル `<name>.md.tmp` を `<name>.md` へリネームします (REQ-NF-005 手順 3) 。
差し替えの成立をもって、処理済み状態を `ChatlogCache` へ記録します (DR-14) 。

記録するのは `STRIP_CACHE_STATUSES` の値であり、本体の frontmatter には書きません。
キャッシュのキーはファイルパスで、他スキルと同一の `ChatlogCache` 機構を用います。

**記録は差し替えの後でなければなりません。**
差し替えに失敗したファイルを処理済みとして記録すると、
次回実行で R-003 により `done` と判定され、strip されないまま残ります。

**dry-run では本フェーズを実行しません。**
したがってキャッシュへの記録も発生しません (Section 3.4) 。

### Phase 6: 退避削除

**規則**: R-010 / R-011 / R-012 / R-013

実行単位の後処理です。全ファイルの評価を終えた後に一括で行います。

**無条件の削除ではありません。** 条件は次のとおりです。

| 規則  | 条件                                               | 動作                                                                 |
| ----- | -------------------------------------------------- | -------------------------------------------------------------------- |
| R-010 | error 0 件・dry-run 未指定・包含関係が成立 (R-013) | 対象ディレクトリ配下の退避を一括削除します                           |
| R-011 | error を計上したファイルが 1 件以上                | 退避をすべて保持します                                               |
| R-012 | R-010 の削除で失敗した退避が 1 件以上              | 件数とパスを報告し、終了コードを成功以外とします                     |
| R-013 | 包含関係が成立しない                               | 退避を保持し、不足するパスを報告します。終了コードを成功以外とします |

**削除の前に包含関係を検査します** (DR-16) 。

```text
{ stripped と判定したファイルのパス } ⊆ { 存在する退避のパス }
```

破れている場合、`stripped` にしたのにバックアップの無いファイルが存在します。
復旧手段を持たないまま本体が書き換わった状態であり、
残りの退避を削除すると被害が拡大するため、削除を見送ります。

検査に用いるパスは Phase 2 の判定結果に含まれ、追加の追跡を要しません。
退避の一覧は削除のために取得するものと同一です。

**件数の比較では代替できません。**
前回中断で残った退避・Phase 4 と Phase 5 の間での中断・他プロセス由来の退避により、
退避の件数は `stripped` の件数と一致しません。いずれも正常な状態です。
件数の下限比較も、余剰と欠損が相殺するため採りません。

削除範囲は対象ディレクトリ配下の退避 **全件** です (DD-02) 。
REQ-C-008 により対象が単一の agent・年月に限定されるため、退避パスの個別追跡を要しません。

削除は全件について試行し、1 件の失敗で残りを中断しません (DR-10) 。
削除失敗は分類に加えません。実行単位の後処理であり、粒度が異なるためです。

**dry-run では本フェーズを実行しません。** 退避自体を作成していないためです。

### Phase 7: 結果報告

**規則**: なし (集計)

4 分類の件数、除去前後の合計バイト数、退避削除の結果を報告します (REQ-F-006) 。

全件処理の判定式が成立することを確認します。

```text
stripped + done + passthrough == total  かつ  error == 0
```

dry-run では加えて、ファイルごとのパス・判定結果・判定理由・除去範囲 (開始行・終了行) ・
除去バイト数を出力します (REQ-F-005) 。

## 3. dry-run の扱い — ハウスパターンからの意図的な逸脱

### 3.1 既存スキルのパターン

既存スキル (set-frontmatter / classify / normalize) は
「各フェーズが `dryRun` を受け取り、自分で分岐する」形を採ります。
AI 呼び出しをスキップし、`logger.dryrun` でログのみ出力し、`stats.skip` に計上します。

### 3.2 strip が採る形

strip はこのパターンを採りません。

| Phase | 内容                 | dry-run           | 通常実行 |
| ----- | -------------------- | ----------------- | -------- |
| 0     | 受理ゲート           | 実行              | 実行     |
| 1     | 一覧取得・キャッシュ | 実行              | 実行     |
| 2     | 判定                 | 実行 (同一)       | 実行     |
| 3     | 退避作成             | **呼び出さない**  | 実行     |
| 4     | strip 済みログ作成   | **呼び出さない**  | 実行     |
| 5     | 差し替え・記録       | **呼び出さない**  | 実行     |
| 6     | 退避削除             | **呼び出さない**  | 実行     |
| 7     | 結果報告             | 実行 (時制のみ差) | 実行     |

Phase 3 から Phase 6 は **呼び出し側 (main) がスキップ** します。
フェーズ内部に `if (dryRun)` を置きません。

副作用を持つフェーズが連続して並ぶため、境界は
「Phase 2 までが判定、Phase 3 から Phase 6 が副作用、Phase 7 が報告」と単純になります。

### 3.3 逸脱の理由

理由は 2 つあります。

**第一に、F-04 への対応です。**
フェーズ内部で分岐すると、判定と副作用が同一関数に同居します。
この構造は「dry-run のときだけ通る経路」を生み、通常実行との乖離を検出できません。
spec 3.2 が「副作用の有無のみを呼び出し側で分岐しなければならない」と定めたのは、
この構造を禁じるためです。

**第二に、strip の判定が AI を必要としないためです。**
既存スキルの dry-run 分岐は、本質的には「高コストな AI 呼び出しの回避」です。
strip の判定は純ロジックであり、回避すべきコストがありません。
したがって Phase 2 を省略する理由がなく、全件を本番と同一規則で評価できます。

既存の `filter` モードの dry-run (`filter-chatlogs.ts:155-159`) は
「claude CLI を呼ばず全件を `stats.skip` に計上する」形ですが、
**strip はこれに倣ってはなりません**。REQ-F-005 と正面から矛盾します。

> **次に読む人へ**: この逸脱は意図的です。
> 「他スキルと揃っていない」ことを理由に Phase 3 / 4 の内部へ `if (dryRun)` を
> 差し戻すと、F-04 の指摘が再発します。

### 3.4 キャッシュ書き込み

dry-run では処理済み状態をキャッシュに記録しません (REQ-F-005) 。
記録した場合、次回の通常実行が全件 `done` となり、strip が実行されません。

Phase 3 を呼び出さない設計により、この要件は構造的に満たされます。
キャッシュ書き込みは Phase 3 の内部にのみ存在するためです。

## 5. 配置と再利用

### 5.1 strip は filter-chatlogs のサブコマンド

strip は新規スキルではなく、`filter-chatlogs` の 3 つ目のサブコマンドです。
REQ-NF-001 が「既存の近接実装と同一の主処理構成を採る」と定めています。

- 配置: `skills/filter-chatlogs/scripts/` 配下
- CLI: `SKILL.md` の argument-hint を `[noise-filter|filter|strip]` に拡張
- 引数スキーマ: `filter-chatlogs.ts:59-62` の `_SCHEMA` パターンに倣う
- `dryRun` は共通 `parseArgs` が既に解釈済み (`args-schema.types.ts:29`)

### 5.2 型定義

| 対象                   | 配置                                  | 備考                                |
| ---------------------- | ------------------------------------- | ----------------------------------- |
| `StripStats`           | `scripts/types/stats.types.ts`        | `BaseStats` の **兄弟**。継承しない |
| `StripCache`           | `scripts/types/cache.types.ts`        | `CLEResult` と同じ場所              |
| `STRIP_CACHE_STATUSES` | `scripts/types/cache.const.types.ts`  | const object + 派生ユニオン型       |
| 判定結果の型           | `scripts/types/strip.types.ts` (新設) | `outcome` / `reason` / 除去範囲     |

`StripStats` を `BaseStats` から継承してはなりません。
`BaseStats.skip` は「dry-run により実行しなかった数」を意味し、
strip の `done` (処理済み・モード非依存) と衝突します。
これは DR-15 が Option D として明示的に却下した命名です。

```ts
export interface StripStats {
  total: number;
  stripped: number;
  done: number;
  passthrough: number;
  error: number;
}
```

### 5.2.1 境界検出の定数

`## Summary` と定型部マーカーは実装ファイルに直書きしてはなりません (spec Section 4.2) 。

```text
skills/filter-chatlogs/scripts/constants/strip.constants.ts
  STRIP_BOUNDARY_HEADING = '## Summary'
```

## 7. 誤りやすい点

### 7.1 `_status` を frontmatter に書いてはならない

strip 済みを表す `_status: stripped` を本体の frontmatter に付与する設計は
**DR-14 により破棄済み** です。

- DR-14: 「`_status` を本体の frontmatter に付与しません。DR-04 の決定を破棄します」
- DR-14: 「strip が本体へ加える変更は、本文先頭から最初の `## Summary` 直前までの除去のみとします」
- AC-024: 「strip 済みファイルの frontmatter が strip 前と同一である」(同一性比較で判定)

処理済み状態は Phase 5 で `ChatlogCache` へ記録します。

**この誤解が生じやすい理由**: requirements.md に DR-14 以前の記述が 5 箇所残存しています
(Scope 26-27 行 / System Context Diagram 71 行 / REQ-F-002 191 行 / AC-013 Gherkin 819-825 行 /
AC-017 Gherkin) 。うち REQ-F-002 の記述は AC-024 と正面から矛盾します。

> 追跡: issue `cle-ax1` にて requirements.md v5.3.1 で一掃済みです。
> Superseded 済みの REQ-F-011 / REQ-C-005 配下には歴史的記録として残存します。

### 7.2 受理ゲートを列挙の後に置いてはならない

R-001 は対象ファイルの列挙より前に評価しなければなりません (Section 4.2) 。

一覧取得を先頭に置くと、拒否されるべき実行でも未検証範囲のファイル一覧が出力に現れます。
仕様は「列挙後に拒否した場合、拒否の意味が失われる」と明記しています。

### 7.3 退避削除は無条件ではない

Phase 6 は「退避を削除する」フェーズではなく、
「**error が 0 件のときに限り** 退避を削除する」フェーズです。

error が 1 件でもあれば退避を全保持します (R-011) 。
削除失敗時は報告と終了コードの変更を伴います (R-012) 。

## 1. Overview

### 1.1 Purpose

本仕様書は `filter strip` サブコマンドの **振る舞い規則** と **分類意味論** を定義します。

対象は、エクスポート済みチャットログ Markdown の冒頭にある set-frontmatter 由来の定型プロンプト部です。
これを除去し、実質的な会話内容のみを残します。

### 1.2 Scope

本仕様書が定義するのは、次の 4 点です。

- 入力ファイルを 4 つの結果 (stripped / done / passthrough / error) のいずれかへ分類する規則と、実行拒否
- 分類の評価順序と、順序を変更できない理由
- 各分類における観測可能な副作用 (ファイル書き込み・退避・退避削除)
- 実行モード (通常モードと復帰専用モード) の分岐と、それぞれで適用される規則の範囲

実装の詳細は対象外です。関数名・型・ファイル配置は Section 2.3 と Section 2.5 に限って言及します。

## 2. Design Principles

### 2.1 Classification Philosophy

本機能は 6000 件規模の破壊的な in-place 書き換えを伴います。
したがって分類の設計は **除去してよい根拠が積極的に確認できた場合にのみ除去する** という原則に立ちます。

この原則から次の 3 つの帰結が導かれます。

1. 判定は否定条件の連鎖として構成し、確証が得られない入力はすべて無変更で通します
2. 曖昧な入力を推測で除去せず、passthrough または error に倒します
3. 検証済みでないデータ範囲に対しては、処理を試みる前に実行そのものを拒否します

### 2.2 Design Assumptions

本仕様は次の前提のうえに成立します。前提が崩れた場合は再検証を要します。

| 前提                                                         | 根拠                                         |
| ------------------------------------------------------------ | -------------------------------------------- |
| 定型部の終端は最初の `## Summary` 見出しで安定して判定できる | claude/2026-07 の 11671 件実測 (REQ-C-004)   |
| 定型部マーカーは `## TOPICS ASSIGNMENT RULES` である         | 正本テンプレートに存在 (REQ-F-000)           |
| 退避ファイルと一時ファイルは走査対象に混入しない             | 走査は `*.md` を対象とし、拡張子が一致しない |
| frontmatter は平坦なスカラー構造である                       | 実測 300 件標本で確認 (Section 5 の Edge 10) |
| 対象は単一の agent かつ単一の年月に限定される                | REQ-C-008 が実行時に強制する                 |

#### DD-01 の検討経緯

> **本項は DR-14 により不要となりました**。strip は frontmatter を再構築しないため、
> キー列挙の手段を要しません。以下は DR-14 以前の記録です。

REQ-C-005 は「入力の既存キー順の末尾に処理済みマーカーを加えた並び順」の構築を求めます。
しかし frontmatter を保持するクラスは値の取得・設定・削除のみを公開し、キーの列挙手段を持ちません。

検討した選択肢は次の 3 つです。

- Option A: クラスにキー列挙メソッドを追加します (**採用**)
- Option B: 呼び出し側が本文分離と YAML 解析により独自にキー順を得ます
- Option C: frontmatter 生成側に追記フィールドのオプションを設けます

Option A を採る理由は、追加が小さく REQ-C-005 の文言をそのまま満たせ、他スキルからも再利用できるためです。
Option B は解析が二重化し、二重管理のリスクを負います。
Option C は「呼び出し側が並び順を構築する」という REQ-C-005 の文言とずれます。

#### DD-02 の検討経緯

当初の REQ-F-010 (v1.8.0) は削除条件を「当該実行で処理した全ファイルの `_status` が `stripped`」と定めていました。
しかし passthrough と判定されたファイルは書き込みを受けず、処理済みマーカーを持ちません。
実測では対象 6398 件に対し passthrough が 3890 件あるため、この条件はほぼ成立せず削除が発動しません。

この問題を受け、削除条件を error 0 件へ戻し、削除範囲を対象ディレクトリ単位の一括操作としました。
REQ-C-008 により対象が単一の agent・年月に限定されるため、
配下の退避はすべて strip の作業対象であり、個別追跡なしに一括削除できます。

本決定は DR-08 として正式な Decision Record に昇格し、
requirements.md も v2.0.0 で REQ-F-010 を再定義しています。
DR-06 の決定 1 (`_status` 基準) は DR-08 により破棄されました。

**Status Values:**

- `Active` — 本仕様書において現に効力を持ちます
- `Promoted → DR-xx` — 正式な Decision Record へ昇格しました
- `Obsolete (DR-xx)` — 後続の決定により不要となりました

## 3. Behavioral Specification

### 3.1 Input Domain

- Input Type: 単一 agent・単一年月のディレクトリ配下にある UTF-8 の Markdown ファイル群
- Assumptions:
  - 各ファイルは frontmatter を持つ場合と持たない場合があります
  - 改行コードは CRLF / LF のいずれもあり得ます
  - 退避ファイルと一時ファイルは走査結果に含まれません
  - 同一ファイルに対する並行実行は想定しません

### 3.2 Output Semantics

- Output Meaning: 各入力ファイルは相互に排他的な 4 つの結果のいずれかに分類されます。
  加えて実行そのものが拒否される場合、いかなるファイルも分類されません。

- Possible Outcomes:

| 結果        | 意味                                                           | 内容の変更 | 退避の作成 |
| ----------- | -------------------------------------------------------------- | ---------- | ---------- |
| stripped    | 定型部を除去し、処理済み状態をキャッシュに記録しました         | あり       | あり       |
| done        | 既に strip 済みと判定し、再処理を回避しました                  | なし       | なし       |
| passthrough | 除去対象外と判定し、無変更で通しました                         | なし       | なし       |
| error       | 前提の破れまたは除去結果の異常を検出し、書き換えを見送りました | なし       | なし       |
| (実行拒否)  | 受理範囲外の起動であり、走査自体を行いませんでした             | なし       | なし       |

分類は判定規則と 1 対 1 で対応します (DR-15) 。

| 分類        | 該当規則      | 意味                                      |
| ----------- | ------------- | ----------------------------------------- |
| stripped    | R-008         | 定型部を除去しました                      |
| done        | R-003 / R-004 | 既に strip 済みであり、再処理を回避します |
| passthrough | R-005 / R-006 | 定型部を持たず、除去の対象になりません    |
| error       | R-002 / R-007 | 前提の破れまたは除去結果の異常です        |

`done` と `passthrough` はいずれも内容を変更しませんが、意味が異なるため分類を分けます。
`done` は過去に除去済みであることを表し、`passthrough` は除去対象でないことを表します。
両者を統合すると、除去した実行と全件が処理済みであった実行をサマリー上で区別できません (DR-15) 。

`done` は dry-run 専用の分類ではありません。通常実行のサマリーにも計上します。

- dry-run Semantics:

dry-run 指定時は、すべての結果について内容を変更せず、退避も作成せず、
キャッシュへ処理済み状態を記録しません。

分類そのものは通常実行と同一の規則で決定します。
分類ロジックは単一の判定関数に閉じなければならず、
副作用の有無のみを呼び出し側で分岐しなければなりません。
分類を dry-run 専用の経路で実装した場合、通常実行との判定の乖離を検出できません。

dry-run と通常実行の差異は、`stripped` の表示上の時制に限られます。
dry-run では当該ファイルがまだ除去されていないため、
「除去する」という未来の表現を用います。
`done` は過去の事実であるため、両モードで同一の表現を用います。

集計構造は両モードで一致しなければなりません。
モードによって分類が異なる場合、dry-run の結果から通常実行の結果を予測できず、
事前検証としての用途が失われます (REQ-F-005) 。

## 4. Decision Rules

<!--

Rule IDs are referenced in Traceability and Edge Cases.
-->

### 4.1 実行単位の規則

評価は次の順序に従わなければなりません。

| Rule ID | Step | Condition                                                                | Outcome                                          |
| ------- | ---: | ------------------------------------------------------------------------ | ------------------------------------------------ |
| R-001   |    1 | 年月が省略されている、または入力ディレクトリの override が指定されている | 実行を拒否し、対象を列挙せず、1 件も変更しません |

R-001 は対象ファイルの列挙より前に評価しなければなりません。
列挙後に拒否した場合、未検証範囲のファイル一覧が出力に現れ、拒否の意味が失われるためです。

#### 実行モード (R-014 / R-015)

`filter strip` は 2 つの実行モードを持ちます (DR-23) 。モードは `--recover-orphans` の指定で決まります。

| Rule ID | Condition                        | Outcome                                                        |
| ------- | -------------------------------- | -------------------------------------------------------------- |
| R-014   | `--recover-orphans` を指定しない | 通常モード。R-002 以降のすべての規則を適用します               |
| R-015   | `--recover-orphans` を指定する   | 復帰専用モード。孤立退避を復帰させて終了し、strip を行いません |

**孤立退避の定義**: 対象ディレクトリ配下に `<name>.md` が存在せず、`<name>.md.bak` または
`<name>.md.tmp` が存在する状態を指します。REQ-NF-005 の手順 2 と 3 の間で中断した場合に生じます。

**通常モード (R-014)** では、孤立退避を検出した場合に当該 `<name>` を error として計上し、
パスを報告します。列挙は `.md` を対象とするため、孤立退避は R-002〜R-008 のいずれにも到達しません。
検出しない場合、error が 0 件のまま R-010 の一括削除に到達し、復旧材料の退避が失われます。

**復帰専用モード (R-015)** では、次の順序で処理します。

1. R-001 の受理ゲートを評価します。対象ディレクトリの特定に `<agent> <YYYY-MM>` が必要なためです
2. 孤立退避のうち `<name>.md.bak` が存在するものを `<name>.md` へリネームして復帰させます
3. 復帰件数と対象パスを報告して終了します

復帰専用モードは R-002〜R-013 のいずれも評価しません。strip を行うには、利用者が復帰の結果を
確認したうえで `--recover-orphans` を指定せずに再実行します。

復帰の対象は `.bak` が存在する場合に限ります。`.tmp` のみが残る場合は復帰元が存在しないため
復帰させず、報告のみとします。`.bak` と `.tmp` が併存する場合は `.bak` を採用し、`.tmp` は残置します。

`--dry-run` と併用された場合、復帰せず、復帰対象の件数とパスの報告にとどめます。

R-014 と R-015 は排他です。復帰専用モードでは通常の分類をしないため、孤立退避の error 計上
(R-014) は発生しません。

### 4.2 ファイル単位の規則

R-001 を通過した各ファイルについて、次の順序で評価します。

| Rule ID | Step | Condition                                                      | Outcome     |
| ------- | ---: | -------------------------------------------------------------- | ----------- |
| R-002   |    1 | frontmatter を持たない                                         | error       |
| R-003   |    2 | キャッシュに処理済みの記録が存在する                           | done        |
| R-004   |    3 | 対応する退避ファイルが既に存在する                             | done        |
| R-005   |    4 | 本文に `## Summary` が 1 つも存在しない                        | passthrough |
| R-006   |    5 | 本文先頭から最初の `## Summary` 直前までに定型部マーカーが無い | passthrough |
| R-007   |    6 | 除去後の本文が空である、または除去率が 99% を超える            | error       |
| R-008   |    7 | 上記すべてに該当しない                                         | stripped    |

順序の変更は許されません。根拠は次のとおりです。

- R-002 を先頭に置く理由は 2 つあります。
  frontmatter の欠落はパイプラインの前提が破れた状態であり、
  後続の判定を試みる前に検出すべきものです。
  なお R-003 の処理済み判定はキャッシュを参照するため (DR-14) 、frontmatter に依存しません。
- R-003 を R-004 より先に置く理由は、退避が削除された後も冪等性を保つためです。
  退避のみを根拠にすると、R-010 による削除後の再実行で strip 済みファイルが再処理されます。
  R-010 は対象ディレクトリ配下の退避を一括削除するため、
  退避を唯一の判定材料とすると再実行時に判定材料が失われます。
- R-005 を R-006 より先に置く理由は、`## Summary` が無ければ除去範囲を定義できず、
  マーカーの探索範囲そのものが定まらないためです。
- R-007 を R-008 より先に置く理由は、安全弁が書き込みの前段でなければ機能しないためです。

#### 境界検出の規則 (REQ-C-004)

R-005 と R-006 が用いる検出は、次の規則に従わなければなりません。

| 対象           | 検出規則                                                         |
| -------------- | ---------------------------------------------------------------- |
| `## Summary`   | 行頭完全一致 (`^## Summary$`) の **最初の出現** を境界とします   |
| 定型部マーカー | 行頭完全一致 (`^## TOPICS ASSIGNMENT RULES$`) の出現を確認します |

**Markdown を構文解析しません**
コードフェンス内・引用内・リスト内・ユーザー発話本文内であるかは解釈しません。

この単純化は claude/2026-07 の実測に基づきます (REQ-C-004) 。

| 検証項目                                             | 実測                         |
| ---------------------------------------------------- | ---------------------------- |
| 定型部保有ファイルで最初の `## Summary` がフェンス内 | 0 件                         |
| 引用・インデント付きの定型部マーカー                 | 0 件                         |
| `## Summary` 見出しの表記ゆれ                        | 3 件 (いずれも strip 対象外) |

構文解析を採らない理由は、パーサの導入が依存と解釈差分を増やし、
破壊的処理のリスクをむしろ高めるためです。
解釈の余地を排した単純規則のほうが、誤 strip の可能性を低く保てます。

マーカーの存在確認だけでは定型部であることを証明できませんが、
本仕様は保守側に倒す設計により誤 strip を回避します。
マーカーが最初の `## Summary` より後ろにある場合は passthrough とします (Edge 13)。
本文が偶然 `## Summary` で始まる場合もマーカー不在により passthrough となります (Edge 12)。

両文字列は実装ファイルに直書きせず、定数として定義しなければなりません。
テンプレート変更時の変更箇所を 1 箇所に閉じるためです。

**前提が破れる条件**: `set-frontmatter` の定型部テンプレート、
または `filter` の削除パターンが変更された場合は再検査を要します (REQ-C-004) 。
未検証のデータセットへの適用は R-001 が実行時に拒否します。

#### 除去率の定義

R-007 の除去率は次の式で算出します。

```text
除去率 = 除去バイト数 ÷ 本文バイト数
```

本文バイト数は frontmatter を除いた部分の長さです。
frontmatter の長さに左右されず、除去範囲そのものの比率を評価するためです。

なお REQ-F-001 の Rationale が示す「定型部はファイルサイズの平均 77.8%」は
ファイル全体を分母とする別の指標です。
実測では両者の差は小さく、除去対象 6398 件において
本文分母の平均が 77.60%、ファイル分母の平均が 77.26% です。

#### 除去率の実測分布 (claude/2026-07)

除去対象 6398 件における除去率 (本文分母) の分布は次のとおりです。

| 区間      | 件数 |
| --------- | ---- |
| 50 - 79%  | 4435 |
| 80 - 89%  | 1919 |
| 90 - 94%  | 42   |
| 95 - 98%  | 2    |
| 99 - 100% | 0    |

| 統計値 | 本文分母 |
| ------ | -------- |
| 平均   | 77.60%   |
| 中央値 | 75.90%   |
| p95    | 87.28%   |
| p99    | 89.62%   |
| 最大   | 96.23%   |

**現データセットにおいて R-007 の除去率条件は発火しません。**
最大が 96.23% であり、閾値の 99% まで 2.77 ポイントの余裕があります。
除去後の本文が空になるファイルも 0 件です。

この事実は 2 つの意味を持ちます。

第一に、閾値 99% は現データセットに対して **安全側に十分な余裕** を持ちます。
正常な入力を error に倒す誤検出は発生しません。

第二に、閾値 99% は **上側の異常しか検出しません**。
分布の最大が 96.23% であることは、境界判定が壊れて本文の大半を除去した場合でも、
除去率が 99% に達しなければ検出されないことを意味します。
安全弁として機能するのは事実上「除去後の本文が空になる」条件のみです。

閾値を下げる案は採りません。
95% とした場合、実測 2 件が error となりますが、
それらが誤削除であるか正常であるかを判別する根拠がありません。
error は R-011 により退避の一括削除を止めるため、
根拠なく閾値を下げると正常な実行が毎回中断します。

除去率は「異常の可能性を示す指標」であり、
誤削除そのものを判別する手段ではありません。
誤削除の防止は R-005 / R-006 の境界検出が担い、
R-007 は判定ロジックが破綻した場合の最終的な安全弁として位置づけます。

R-008 が成立したファイルに対する副作用は、次の順序で発生しなければなりません。

| Rule ID | Step | Action                                   |
| ------- | ---: | ---------------------------------------- |
| R-009   |    1 | 除去後の内容を一時ファイルへ書き出します |
| R-009   |    2 | 元ファイルを退避先へ移動します           |
| R-009   |    3 | 一時ファイルを元のファイル名へ移動します |

この順序により、いかなる中断点でも元の内容または完全な除去後の内容の一方が必ず残ります。
手順 2 と 3 の間で中断した場合、元のファイル名は存在せず、退避に元の内容が残ります。

処理済み状態の記録はキャッシュに対して行い、本体の frontmatter は変更しません (DR-14) 。
frontmatter を再構築しないため、キー順の明示的な構築を要しません。

#### frontmatter の不変性 (AC-024)

strip 済みファイルの frontmatter は strip 前と **同一の内容** でなければなりません。

判定はバイト単位ではなく、`ChatlogFrontmatter` による同一性比較で行います。
CRLF での入力が`normalizeLine`による`LF`に正規化されるため、バイト単位の一致が機能しません (REQ-NF-003 / Edge 11)。
改行コードの正規化は決定事項であり、これを取りやめません。

同一性は次の条件で判定します。

| 条件       | 内容                                                                          |
| ---------- | ----------------------------------------------------------------------------- |
| キー集合   | 両者のキー集合が一致すること                                                  |
| 値         | 各キーについて値が一致すること (`string` は `===`、`string[]` は長さと各要素) |
| キーの順序 | **比較対象に含めません**                                                      |

キーの順序を含めない理由は、strip が frontmatter を再構築せず順序が物理的に不変であるためです。
順序を判定条件に含めると、将来 frontmatter を経由する処理が入った際に過剰な制約となります。

比較を呼び出し側でインラインに実装してはなりません (REQ-C-001) 。
文字列表現の比較に依存すると、改行コード・引用符・インデントの差異が
内容の変化として誤検出されます。

### 4.3 実行終了時の規則

全ファイルの評価を終えた後、次の順序で評価します。

| Rule ID | Step | Condition                                                                             | Outcome                                                                    |
| ------- | ---: | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| R-010   |    1 | error が 0 件であり、dry-run が指定されておらず、かつ退避の包含関係が成立する (R-013) | 対象ディレクトリ配下の退避を一括削除します                                 |
| R-011   |    2 | error を計上したファイルが 1 件以上ある                                               | 退避をすべて保持します                                                     |
| R-012   |    3 | R-010 の削除で失敗した退避が 1 件以上ある                                             | 失敗件数と対象パスを報告し、終了コードを成功以外とします                   |
| R-013   |    4 | 退避の包含関係が成立しない                                                            | 退避を保持し、不足する退避のパスを報告します。終了コードを成功以外とします |

R-010 の削除範囲は **対象ディレクトリ配下の退避ファイル全件** です (DD-02)。

#### 退避の包含関係 (R-013)

削除の前に、次の包含関係が成立しなければなりません (DR-16) 。

```text
{ stripped と判定したファイルのパス } ⊆ { 存在する退避のパス }
```

包含が成立しない場合、`stripped` と計上したにもかかわらず対応する退避を持たないファイルが
存在することを意味します。
当該ファイルは復旧手段を持たないまま本体が書き換わった状態であり、
この状態で残りの退避を一括削除すると被害が拡大します。

**件数の比較では代替できません。**
退避の件数が `stripped` の件数と一致しない経路が 3 つあるためです。

| 経路                            | 影響                                                     |
| ------------------------------- | -------------------------------------------------------- |
| 前回実行が error で終了した     | R-011 により退避が全保持され、次回は `done` となり計上外 |
| Phase 4 と Phase 5 の間での中断 | 退避は存在するが `stripped` に計上されていない           |
| 他プロセス・手動作業由来の退避  | 仕様は退避の作成元を区別しません                         |

いずれも正常な状態であり、件数の等式で異常と判定するのは誤りです。
件数の下限を検査する形も、余剰と欠損が相殺するため採りません。

検査に用いるパスは判定の結果として既に保持しており、追加の追跡を要しません。
退避の一覧は削除のために取得するものと同一であり、追加の走査も生じません。
REQ-C-008 により対象は単一の agent・年月のディレクトリに限定されるため、
配下の退避はすべて strip の作業対象であり、退避パスを個別に追跡する必要がありません。

前回実行の中断により残った退避も削除対象に含みます。
当該実行が全件を error なく処理し終えた時点で、対象ディレクトリは正常な strip 済み状態であり、
古い退避を保持する理由が無いためです。

passthrough と done の件数は削除の可否に影響しません。
判定材料は error の有無と、退避の包含関係 (R-013) の 2 つです。

#### 退避削除と処理済み判定の関係

R-004 は既存の退避を処理済みの根拠として用いる一方、R-010 はその退避を削除します。
一見すると、保護判定に用いた証拠を実行の最後に消す設計のように見えます。

この矛盾は R-003 を R-004 より先に置く順序制約により解消されます (Section 4.2) 。
処理済みの一次的な判定材料はキャッシュであり、退避ではありません (DR-14) 。
キャッシュが健在である限り、退避が削除された後も再実行は冪等です。

退避は二次的な判定材料であり、キャッシュを持たないファイルに対する保険として機能します。

**縮退挙動**: キャッシュが失われた場合 (別環境での実行・キャッシュの削除・
`DEFAULT_CACHE_ROOT` の変更) 、R-003 と R-004 が同時に無効となります。
このとき strip 済みファイルは再評価されます。

再評価の結果は次のとおりです。

| 対象                                          | 再評価の結果                                   |
| --------------------------------------------- | ---------------------------------------------- |
| 通常の strip 済みファイル                     | R-006 により passthrough。本文は破壊されません |
| 先頭 strip 後もなお定型部が残るもの (Edge 14) | 再び R-008 に到達し、再 strip されます         |

前者が安全である理由は、strip 済みファイルの本文が `## Summary` から始まり、
その手前に定型部マーカーを持たないためです。

後者は実測 11671 件中 0 件であり、現データセットでは該当しません。
ただし定型部マーカーが 2 個目以降の `## Summary` 以降に位置する構造は原理的に起こりえます。
DR-14 は、発生した場合の損失を許容しています。
一次ソースは `~/.claude/projects/` の JSONL であり、re-export による復元が可能です (DR-06) 。

本仕様は R-010 の削除範囲を変更しません。
削除範囲を「当該実行が作成した退避」に限定する案は、退避パスの個別追跡を要し、
DD-02 が REQ-C-008 を根拠に不要と判断した設計を覆します。
守られる対象は同じ 2 件であり、追跡の複雑さに見合いません。

この判断の見直しは Open Question 4 として記録します。

ただし削除の可否判断には R-013 の包含検査を課します (DR-16) 。
キャッシュの健在を前提とするだけでなく、削除の直前に退避の整合性を実行時に確かめます。

#### 全件処理の判定 (DR-15)

全ファイルの評価を終えた時点で、次の式が成立しなければなりません。

```text
stripped + done + passthrough == total  かつ  error == 0
```

分類が相互に排他的であるため (Section 3.2) 、
この 2 条件により「全ファイルが異常なく評価を完了した」ことを表現できます。

式が成立しない場合、評価されなかったファイルが存在するか、
分類の計上に漏れがあることを示します。

孤立退避 (R-014) は `.md` を持たず列挙されないため `total` に含まれません。当該 error は左辺の
等式には現れず、`error == 0` の条件のみで捕捉されます。2 条件の連言であるため判定は成立します。

復帰専用モード (R-015) では分類をしないため、本判定式を評価しません。

dry-run 指定時は退避自体を作成しないため、削除も行いません。

削除は実行の最後に一括で行わなければなりません。
ファイルごとに逐次削除した場合、途中失敗により「一部だけ削除済み」の状態が生じます。

#### 削除失敗時の扱い (R-012)

一括削除であっても、個別の削除操作は失敗しえます (DR-10) 。
Windows 環境ではファイルロックやアンチウイルスによる占有が想定され、
6000 件規模では一部失敗が現実的に起こります。

削除は全件について試行しなければなりません。
1 件の失敗で残りの削除を中断した場合、削除済みと未削除の混在範囲が実行ごとに変わり、
再実行時の状態把握が困難になります。

削除に失敗した退避が 1 件以上ある場合、失敗件数と対象パスを報告します。
この場合の終了コードは成功以外とします。
削除失敗を報告しないと、退避が残存したか削除されたかを利用者が判別できず、
ディスク使用量の見積もりと次回実行時の前提が崩れます。

削除失敗は Section 3.2 の分類には加えません。
分類は入力ファイル単位の結果であり、実行単位の後処理である削除とは粒度が異なるためです。
また削除失敗は、既に確定したファイル単位の分類結果を取り消しません。
削除は全ファイルの評価を終えた後の後処理であり、その失敗は書き換えの正しさに影響しないためです。

削除に失敗した退避は、次回実行時の一括削除で再び対象となります。

| 11 | 入力の改行コードが CRLF である                   | stripped       | REQ-NF-003           | 検出は改行コードに依存しません。書き出し時に LF へ正規化されます。frontmatter の不変性はバイト単位ではなく同一性比較で判定します (AC-024) |
| 12 | 本文中のユーザー発話が偶然 `## Summary` で始まる | passthrough    | REQ-F-000            | マーカーの確認により保護されます。実例が 1 件確認されています                                                                             |
| 13 | 定型部が最初の `## Summary` より後ろにある       | passthrough    | REQ-F-000, REQ-C-004 | 実測 4 件が該当します。先頭アンカー方式では対象外です                                                                                     |
| 14 | 先頭 strip 後もなお定型部が残る                  | stripped       | REQ-F-009            | 実測 0 件。マーカーが 2 個目以降の `## Summary` 以降にある場合に発生しえます。再実行時はキャッシュにより done となり再処理を防ぎます      |
| 15 | frontmatter を持たない                           | error          | REQ-F-008            | export の出力は frontmatter を必ず持つため、欠落は前提の破れを示します                                                                    |

Edge 10 は現時点で発生しない前提です。
前提が崩れた場合の挙動は本仕様では規定せず、Section 7 に記録します。

Edge 15 を passthrough ではなく error とする根拠を示します。
`originalLogs/` 配下の全ファイルは `export-chatlogs` の `renderMarkdown` により生成されます。
frontmatter のデリミタと `session_id` / `date` は条件分岐の外にあり、無条件に出力されます。
該当箇所は `export-chatlogs/scripts/libs/session-writer.ts` の 57 行目から 62 行目です。
claude / codex / chatgpt の 3 エクスポータはいずれもこの経路を通り、他に本番の書き出し経路はありません。
したがって frontmatter の欠落は「対象外の入力」ではなく「パイプラインの前提が破れた状態」であり、
黙って通すのではなく検出して報告します。

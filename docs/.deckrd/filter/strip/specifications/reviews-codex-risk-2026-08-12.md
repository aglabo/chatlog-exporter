## 1. 最も危険な前提 3 つ

| # | 前提                                                          | 指摘                                                                                                                                                                                                                                                                                        |
| - | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | 最初の `## Summary` が除去境界として安定している              | 実測 11671 件に基づくとはいえ、仕様自体が「現在の claude/2026-07」に強く依存している。テンプレート変更、エクスポータ変更、別 agent、別年月、ユーザー本文中の見出し混入で即座に破綻する。特に「最初の Summary より前にマーカーがある」だけでは、そこまでが本当に定型部だと証明できない       |
| 2 | `## TOPICS ASSIGNMENT RULES` が定型部マーカーとして十分       | 単一文字列に依存しすぎている。テンプレートの見出し名変更、ローカライズ、空白差分、Markdown レベル変更、引用ブロック内出現、ユーザー発話内出現などをどう扱うかが未定義。マーカーが「存在する」ことと「定型プロンプト由来である」ことは同じではない                                           |
| 3 | error が 0 件なら対象ディレクトリ配下の退避を一括削除してよい | **最も破壊的**。「今回作成した退避」と「前回中断で残った退避」と「別処理・手動作業・別バージョンが作った退避」を区別していない。さらに R-004 では既存退避を passthrough として保護材料にしているのに、R-010 では error 0 件ならその既存退避を削除する。保護判定に使った証拠を最後に消す設計 |

## 2. この設計が失敗し得る原因

- 誤った境界検出により、ユーザー本文の先頭部分を定型部として削除する
- テンプレートが微変更され、マーカー未検出で大量 passthrough になり、期待された除去がほぼ行われない
- ユーザー本文中に `## TOPICS ASSIGNMENT RULES` と `## Summary` が偶然または引用として出現し、誤 strip する
- キャッシュが壊れる、移動する、別ブランチ・別環境で共有されないことで、冪等性判定が崩れる
- 退避削除が「今回の実行範囲」ではなく「対象ディレクトリ配下全件」なので、復旧可能性を想定外に失う
- `frontmatter を持たない = error` により、実ログとしては有効な Markdown を処理不能扱いし、大量の error で退避削除も止まる
- CRLF 入力を「書き出し時に正規化」することで、strip 以外の差分が発生する。これは in-place 破壊的変更として過小評価されている
- dry-run と通常実行で、キャッシュ・退避・一時ファイル・削除対象の扱いが本当に同じ分類になるか未定義
- 並行実行を「想定しない」としているだけで、ロックや検出がない場合、同一ディレクトリに対する二重起動で退避・一時ファイル・キャッシュが競合する
- 除去率 99% という安全弁は、誤削除の多くを止められない。例えば 30〜80% の本文破壊は普通に stripped になり得る
- 「実測平均 77.8%」と「本文バイト数基準の除去率」が別指標であるため、99% 閾値の妥当性が弱い
- Edge 14 の「先頭 strip 後もなお定型部が残るが stripped」は危険。仕様上、既知の不完全除去を成功扱いしており、品質保証上の穴になる

## 総括 (codex)

最大の設計リスクは、分類が保守的に見える一方で、`stripped` 判定後と退避一括削除が非常に楽観的なこと。
特に R-010 は「error がない」ことを「復旧手段を消してよい」ことに読み替えており、根拠が弱い。

### 対応候補 A: R-004 と R-010 の整合 (危険な前提 3)

判定: 部分:

codex は「R-004 が退避を保護材料に使うのに R-010 がそれを削除する」ことを自己矛盾と指摘する。
ただし spec 側には既に打ち消し機構がある。

- R-003 (キャッシュ参照) を R-004 より **先に** 置く順序制約が、退避削除後の冪等性を担保する
  (specifications.md Section 4.2 の順序根拠、DR-14)
- REQ-F-009 の Rationale も「`.bak` を唯一の処理済みマーカーとすると冪等性が失われる」ため
  キャッシュへ記録すると明記している

したがって「保護判定の証拠を消す」という指摘は、キャッシュが健在である限り成立しない。

**残る論点**: キャッシュが失われた場合 (別環境・キャッシュ削除・`DEFAULT_CACHE_ROOT` 変更) に、
R-003 と R-004 が同時に無効となった場合、strip 済みファイルを再 strip する経路が残る。
このとき Edge 14 の「先頭 strip 後もなお定型部が残る」2 件は実際に再 strip され、本文を失う。

> **対応方針**: キャッシュ喪失時の縮退挙動を specifications.md に規定するか、
> Open Question として記録する。DR 化の要否はユーザー判断。

### 対応候補 B: 除去率 99% 閾値の実効性 (失敗経路)

判定: 未:

- 30〜80% の本文破壊は R-007 を素通りする。安全弁は「全損」しか止められない
- specifications.md 自身が「実測平均 77.8% はファイル全体を分母とする別指標」と認めており、
  99% という値が本文分母の指標として妥当である根拠は spec / requirements のいずれにも無い

これは Open Question 3 (「除去率 99% の閾値は設定可能とすべきか、固定値でよいか」) と同一の論点だが、
codex の指摘は **閾値の可変性ではなく値そのものの妥当性** を問うており、Q-3 より射程が広い。

> **対応方針**: Open Question 3 の記述を「値の妥当性」まで含むよう拡張する。
> 実測分布 (本文分母での除去率のヒストグラム) が取得できれば、閾値の根拠として spec に追記できる。

### 対応候補 C: CRLF 正規化と AC-024 の衝突 (失敗経路)

判定: 部分:

CRLF 正規化そのものは既知であり、REQ-NF-003 が
「`_cle-libs` の `writeTextFile` は `normalizeLine` を適用するため、除去対象ファイルの改行コードは
書き出し時に正規化されます」と明記している。この点で codex の指摘は「済」。

**残る論点**: REQ-F-009 の **AC-024「strip 済みファイルの frontmatter が strip 前とバイト単位で一致する」**
との衝突。入力が CRLF の場合、`normalizeLine` により frontmatter 部の改行も LF へ変換されるため、
AC-024 はバイト単位では成立しない。

Edge 11 は CRLF 入力を `stripped` と分類し「書き出し時に正規化されます」と記すのみで、
AC-024 との関係に言及していない。

> **対応方針**: AC-024 の「バイト単位」を「改行コード正規化を除きバイト単位」に修正するか、
> Edge 11 に AC-024 の例外を明記する。requirements 側の修正を伴うため要ユーザー判断。

### 外部依存の未定義項目 (対応候補 D)

**判定: 未** (5 件)

codex が挙げた未定義項目のうち、次は spec ではなく **impl フェーズで確定すべき** もの。
現時点で spec への追記は不要だが、impl 着手時に漏らさないよう記録する。

- 退避・一時ファイルの具体的 suffix と衝突時動作 (DR-03 で `.bak` は決定済み、一時ファイルは未定)
- キャッシュのキー設計とファイル移動・リネーム時の扱い
- Markdown 見出し判定の厳密性 (完全一致 / 前後空白 / コードブロック内除外)
- 終了コードの具体値と機械可読出力のスキーマ
- Windows での rename/move の原子性と同一ボリューム制約

> **対応方針**: impl フェーズのチェック項目として持ち越す。spec の Open Questions には追加しない
> (振る舞い規則ではなく実装詳細のため、Section 1.2 の Scope 外)。

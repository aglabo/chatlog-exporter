## 1. Overview

### 1.1 Purpose

本仕様は、mutation testing harness (対象モジュールのソースに変異を 1 件ずつ入れて既存テストを実行し、テストが変異を検出できるかを測る監査ツール) の振る舞いを定める。
このインデックスは次の 3 点を担う。

- 分割ファイルの一覧と、各ファイルが担当する要件の範囲
- ファイルをまたぐ全体の実行順序 (オーケストレーション) と、失敗の伝播規則
- すべての要件 (REQ-F / REQ-NF / REQ-C) の担当ファイルへの対応表 (Requirements Coverage) と、未解決事項の集約

### 1.2 Scope

This specification defines the **behavioral rules** and
**classification semantics** of mutation testing harness.

Implementation details are explicitly out of scope.

## 2. Design Principles

### 2.1 Classification Philosophy

- **元ソースは読むだけ**: 監査はソースを書き換えない。書き込んでよいのは変異体と一時設定だけであり、実行後に元ソースが変わっていないことを機械的に確認する。
- **変異体単位の失敗と監査単位の失敗を分ける**: 1 件の変異体の失敗は記録して続行する。監査そのものが成立しない失敗 (引数・許容リスト・ロック・ベースライン・drift) は非 0 終了として扱う。
- **テストの検出と型検査の検出を混ぜない**: 型検査で落ちた変異体はテストが検出したものとして数えない。
- **生存は悪ではない**: 既定ではレポートする道具として働き、切り分けを終えたモジュールだけを `--strict` でゲートにする。
- **安全装置は後始末より前に置く**: 何かを削除・書き込みする前に、他の実行がそれを使っていないこと (ロック) を確定する。

### 2.2 Design Assumptions

- 対象モジュールのテストは `deno test` で実行でき、失敗時に非 0 で終了する。
- 対象ソースはテストから import で読まれる。ソースを文字列として読むテストは監査の対象外である。
- テスト自身が起こす副作用 (一時ファイル・外部通信・サブプロセス) はテストの責務であり、ハーネスは制限しない。
- 許容リストの一致は「行テキストが同じ」ことしか保証しない。周辺条件の変更で等価性が失われても検出しない (DR-04)。
- 変異体の実行は 1 件ずつ逐次に行う (DR-05)。
- 動作確認済みの実行環境は Deno 2.9.7 である。
- 一時設定は元の設定と同じディレクトリに置き、元の設定の全キーを引き継ぐため、相対パス・既存の import 解決は元の設定と同じ意味を保つ。設定の継承 (他の設定ファイルの参照) は対象外である。
- 監査中、対象ソース・依存・設定・許容リストは変更されない。drift 検査が検出するのは対象ソースの変更だけであり、それ以外の入力の一貫性は保証しない。
- 全件 survived のファイルに対する警告は、差し替えが効いていないことの兆候を示すだけであり、差し替えの有効性を証明しない。
- 変異対象の除外 (テスト・型定義・定数のファイル、正規表現を含む行など) は監査の範囲を縮める。除外した箇所の検出力は測られない。
- テストは決定的であるとする。ベースライン 1 回の成功では不安定なテストを検出できず、偶発的な失敗は killed に数えられうる。

## 3. Behavioral Specification

### 3.1 Input Domain

- Input Type: 開発者または CI が与える、モジュール名 1 つとオプション (`--strict`、`--timeout <秒>`)
- Assumptions:
  - モジュール名は、既定の短縮名の集合 (libs / classify / export / filter / normalize / set) のいずれかである。それ以外は不正な引数として扱う
  - 制限時間は正の整数の秒数である。省略時は 120 秒とする。正の整数でない値は不正な引数として扱う
  - 許容リストはモジュールごとに 1 つ存在しうる。無い場合は空のリストとして扱う
  - 実行はリポジトリのルートから行う

### 3.2 Output Semantics

- Output Meaning:
  - 標準出力には、テキスト形式のレポートだけを出す。機械可読形式 (JSON 等) は出さない
  - ログ・警告・診断は標準エラー出力に出す
  - 終了コードは、監査が成立したか、および `--strict` の条件を満たしたかを表す
- Possible Outcomes:
  - **正常終了 (0)**: 監査が成立し、既定では生存の有無によらない。`--strict` では未許容の生存・有効判定 0 件・古いエントリがいずれも無い
  - **非 0 終了**: 次のいずれか
    - 引数・モジュール名の不正
    - 許容リストの読み込みエラー
    - ロックの取得失敗
    - ベースラインの失敗 (テスト失敗または 0 件)
    - drift の検出
    - `--strict` の条件違反
  - **終了コード 130**: 中断 (SIGINT) された場合。そこまでの結果でレポートを出す
  - **変異体ごとの判定**: killed / survived / timeout / error / compile-error の 5 種。これらは終了コードを直接は決めない (`--strict` の有効判定 0 件の条件を除く)

| R-014   | 割込 | 実行中に SIGINT を受けた (R-004 のロック取得以降) | 実行中の変異体の後始末、drift 検査を行い、そこまでの結果でレポートを出してからロックを解放し、終了コード 130 で終了する。ハッシュ記録 (R-006) の完了前に受けた場合は、進行中の掃除・ハッシュ記録を終えてから drift 検査を省き、中断の事実だけをレポートしてロックを解放し、130 で終了する (execution R-227 が正) | execution             |

No reordering is permitted.

**順序に関する補足規則**:

- ロックの取得 (R-004) は、すべての書き込み・削除に先行する。ロック取得前に中止する場合 (R-001〜R-003)、ファイルシステムへの書き込みを行わない。
- 取得したロックは、R-007 での中止、R-014 での中断、例外を含むあらゆる経路で解放する。ただし、強制終了で残ったロックの扱いは execution が定める。
- 変異体の処理 (R-009) は逐次であり、並列に実行しない (DR-05)。
- R-007 で中止する場合も drift 検査 (R-011) を行う。ベースラインのテストが元ソースを書き換えていれば drift として報告する。
- R-004 の後の処理 (掃除・ハッシュ記録・レポート出力) が失敗した場合は監査単位の失敗として非 0 で中止し、ロックは解放する (execution DD-14)。

# BDD 開発サイクル（RGRサイクル）

## 適用トリガー

以下のいずれかの作業を行う場合、必ず BDD RGRサイクルを実施する。

| 作業種別               | 例                                       |
| ---------------------- | ---------------------------------------- |
| 新機能追加             | 新しい関数・クラス・モジュールの実装     |
| バグ修正               | 既存ロジックの誤りを正す変更             |
| リファクタリング       | 外部仕様を変えずに内部構造を整理する変更 |
| ファイル移動による修正 | モジュール再配置に伴う import パス変更   |

## 免除条件

以下の変更は RGRサイクルの対象外とする。

- `.md` ファイル・JSDoc・コメントのみの変更（ドキュメント変更）
- 設定ファイルのみの変更
- フォーマッタによる純粋なフォーマット整形
- 自動生成ファイルの更新

## RGRサイクルの手順

### Phase 1: Red（テスト先行）

1. テスト対象の関数・クラスのインターフェース（シグネチャ）を確定する
2. プロジェクトのテスト規約に従いテストファイルを作成する
3. テストが失敗することを確認する（実装が存在しないか、期待値と異なること）

```bash
# プロジェクトのテストコマンドでテストが FAIL であることを確認する
```

### Phase 2: Green（最小実装）

1. テストをパスさせる最小限のコードを実装する
   - この段階では「正しい設計」より「テストを通す」ことを優先する
   - 一時的なハードコード等は次の Phase で解消する
2. すべてのテストがパスすることを確認する

```bash
# プロジェクトのテストコマンドでテストが PASS であることを確認する
```

### Phase 3: Refactor（整理）

1. テストを壊さずにコードを整理する
   - `coding-guidelines.md` の規約に準拠させる
   - ハードコードを適切な型・定数に置き換える
   - 重複ロジックを抽出する
2. フォーマットを確認・修正する
3. 全テストが引き続きパスすることを確認する

## ファイル移動時の特例

内容変更を伴わない純粋なファイル移動は、フル RGRサイクルではなく次の手順を実施する。

1. ファイルを移動し、import パスを修正する
2. 全ユニットテストを実行してデグレがないことを確認する

移動に伴いロジックを変更した場合は、変更箇所について通常の RGRサイクルを適用する。

## BDD 実装エージェント

**BDD RGRサイクルが必要な作業は、必ず `bdd-coder` エージェントに委譲する。**

- Claude Code のメインスレッドで直接コードを書かない
- `bdd-coder` エージェントを使うことで、Red → Green → Refactor の各フェーズが確実に実施される
- ファイル移動・import パス変更（ファイル移動時の特例）も同様に `bdd-coder` を使う

### エージェント呼び出しのタイミング

| 状況                                              | 対応                               |
| ------------------------------------------------- | ---------------------------------- |
| 新機能・バグ修正・リファクタリングの実装開始時    | `bdd-coder` エージェントを起動する |
| ファイル移動に伴う import パス修正が必要な時      | `bdd-coder` エージェントを起動する |
| テストが RED のまま次フェーズに進もうとしている時 | 作業を止めてユーザーに確認する     |

### エージェントへの引き継ぎ情報

`bdd-coder` エージェント起動時は以下を必ずプロンプトに含める。

- 作業種別（新機能 / バグ修正 / リファクタリング / ファイル移動）
- テスト対象ファイルと関数・クラス名
- 期待する振る舞い（正常系 / 異常系 / エッジケース）
- 既存テストファイルのパス（存在する場合）
- 使用するテストコマンド

### 1 委譲 = 1 タスク

**タスクが複数ある場合、まとめて委譲しない。1 つずつ委譲し、都度検証してから次へ進む。**

- **他タスクを含む資料を渡さない。** チェックリストファイルを渡す場合は、当該タスク分のみを
  記載したファイルにする。1 ファイルに T-01 と T-02 が併記されていると、プロンプトで
  「T-01 のみ」と指示しても T-02 まで実装される
- **委譲の直後に実際の変更範囲を検証する。** エージェントの自己申告ではなく差分で確認する

  ```bash
  git --no-optional-locks status --short
  git --no-optional-locks diff --stat HEAD -- <対象ディレクトリ>
  ```

- 想定外のファイルが変更されていたら、次のタスクを委譲せず、まずユーザーに報告する

**根拠**: 2026-08-18 の cle-vyt で、T-01（新規ファイル作成のみ）を委譲したエージェントが
T-01 と T-02 が併記されたチェックリストを渡されたため T-02 相当まで実装し、
最終報告では「`write-stripped.ts` は触っていない」と申告した。
自己申告と実際の差分が食い違うことは起こりうる前提で運用する。
